# Как мы работаем (Contributing)

Правила работы с кодом, ветками, PR и деплоем для команды **topdim**.

## 🎯 Главное правило

`main` — **единственная стабильная ветка и источник продакшена**. Всё, что в
`main`, считается готовым к деплою. **Никто не пушит в `main` напрямую** —
только через Pull Request.

> ⚠️ Сейчас `main` не защищён технически (для принудительной защиты нужен
> GitHub Pro/Team). Поэтому правило держится на **дисциплине** — соблюдаем все.

## 🌿 Ветки

Работаем в **коротких** ветках от `main`:

| Префикс | Для чего |
|---|---|
| `feature/<что>` | новая функциональность |
| `fix/<что>` | багфикс |
| `chore/<что>` | инфраструктура, зависимости, CI |
| `docs/<что>` | документация |

- Ветка живёт недолго (1–3 дня), маленький объём изменений.
- Коммиты осмысленные, в стиле **Conventional Commits**: `feat:`, `fix:`,
  `chore:`, `refactor:`, `docs:`…

## 🔀 Как попасть в `main` (Pull Request)

1. Запушил ветку → открыл **Pull Request** в `main`.
2. **CI должен быть зелёным** (Backend tests + Frontend lint/build). Красный
   CI = не мержим.
3. **Ревью** — минимум 1 апрув коллеги.
4. **Squash-merge** → один чистый коммит в `main`.
5. **Удалить ветку** после мержа.

## 🤖 PR-гейт (авто-ревью, advisory)

Воркфлоу `.github/workflows/claude-code-review.yml` запускает агента
`pr-gatekeeper`: ревьюит дифф против правил проекта и DoD, постит
`## Вердикт: PASS|FAIL` комментарием, красит чек `claude-review`.

- Ревьюит **всех коллабораторов, КРОМЕ владельца `Uzabr`** (сам себе ревьюер) **и
  ботов** (включая dependabot). Новый коллаборатор автоматически под ревью — без
  ручного вайтлиста. Черновики пропускаются.
- Гейт **advisory**: красный чек кнопку Merge **не блокирует** (protection нет),
  НО `FAIL` блокирует ручной деплой (см. guard ниже). Требует секрет репо
  `CLAUDE_CODE_OAUTH_TOKEN`.
- `.github/CODEOWNERS` авто-запрашивает ревьюеров по зонам, без энфорса.

## 🚀 Деплой — РУЧНОЙ

Мерж в `main` **НЕ выкатывает** код автоматически: `push` в `main` только
**собирает и пушит образы** в GHCR (валидация). Чтобы задеплоить в прод:

> **GitHub → Actions → «CD — build & push images» → Run workflow → ветка `main`
> → поле `services`** (через пробел; пусто = все 11 сервисов) **→ Run**
> (запускает только владелец).

CD: соберёт образы → запушит в GHCR → по SSH (forced-command) дёрнет EasyPanel
deploy-webhook по каждому сервису. Перед вебхуком deploy-job имеет **guard**:
блокируется, если у коммита `main` PR-гейт вынес `## Вердикт: FAIL`.

- Деплоим **осознанно** — не каждый мерж = деплой, собираем пачкой.
- Почему ручной: branch protection на приватном репо платный, поэтому жёсткий
  гейт стоит на **деплое** — плохой мерж может лечь в `main`, но в прод сам не
  уедет до осознанного запуска.
- После деплоя смотрим логи EasyPanel: сервис поднялся, миграции применились.

## ❌ Чего ИЗБЕГАТЬ

- Прямой `push` в `main` — только через PR.
- Править runtime-конфиг на сервере руками **в обход EasyPanel**
  (`docker service update` и т.п.) — это создаёт **дрейф** и ломает прод.
  Ручные docker-команды — **только для аварий**, не как процесс.
- **Секреты в чат / коммит / Slack / PR.** Секреты живут только в
  **EasyPanel env** и **GitHub Secrets**.
- Коммитить `.env`, ключи, пароли (`.env` уже в `.gitignore` — так и держим).
- Хардкодить секреты-дефолты в `application.yml`
  (`${JWT_SECRET:слабый_дефолт}`).
- Открывать внутренние сервисы наружу. Публичны только **api-gateway** и
  **фронты**; identity/order/payment/pgweb/rabbitmq и т.п. — **внутренние**.
- Откатывать GitHub Actions на мутабельные теги (`@v4`) — они **запинены к
  SHA**, обновляет Dependabot.
- Менять `.github/workflows` походя — это инфраструктура (деплой + секреты),
  ревью обязательно.

## ✅ Чему СЛЕДОВАТЬ

- **Единый владелец конфига:** runtime/секреты → EasyPanel env + GitHub
  Secrets; код/образы → git + CI/CD. Не дублировать одно через другое.
- PR → зелёный CI → ревью → **squash-merge** → удалить ветку.
- Деплой через **CD workflow** вручную, наблюдать health-check/rollback.
- **Dependabot PR-ы** ревьюить и мержить — держать зависимости и экшены
  свежими.
- **Ротировать секреты**, если они где-то засветились.

## ☑️ Чеклист перед мержем PR

- [ ] CI зелёный
- [ ] В диффе нет секретов / `.env` / ключей
- [ ] PR маленький и сфокусированный
- [ ] Есть апрув ревью
- [ ] Squash-merge + удалить ветку

## 🔒 Защита `main` (на будущее)

Для **принудительной** защиты (запрет прямого push, обязательный зелёный CI и
ревью) нужен **GitHub Pro** — там включаются branch protection / rulesets. Без
него защита работает только как договорённость в команде.

**Клиентская подстраховка (пока без Pro):** в репо лежат git-хуки в `.githooks/`.
Включи их **один раз в своём клоне**:

```bash
git config core.hooksPath .githooks
```

После этого локально работают:
- `pre-commit` — блокирует коммит секретов (gitleaks);
- `pre-push` — блокирует **прямой push в `main`** и напоминает открыть PR
  (`gh pr create --base main`). Именно PR запускает CI-гейт и Claude-ревью —
  прямой push их обходит.

Осознанный обход в редком случае: `git push --no-verify` / `git commit --no-verify`.
Хуки клиентские — их нужно включить на **каждой** машине (это не серверная защита).
