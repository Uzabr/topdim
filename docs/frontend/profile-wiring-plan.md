# План: доподключение профиля web-app к существующим эндпоинтам

> Для ИИ-агента. Реализовать в этом воркри (ветка `feat/profile-wiring`), один пункт за раз.
> Все 4 пункта — **фронтовая склейка с УЖЕ существующими бэкенд-эндпоинтами** (бэкенд трогать не нужно).
> Источник: аудит профиля 2026-07-21 (UI есть, но не подключён к API).

## Общие правила
- Работаем только во `frontend/web-app/`. Стек: React 19 + TypeScript + Vite, стор — Zustand (`src/store/*`), API — `src/api/*.ts` (axios-инстанс с интерсептором JWT).
- Формат ответа бэкенда: `{ success, message, data, timestamp }` (обёртка `ApiResponse`) — распаковывать `.data`.
- Текущий пользователь на бэке определяется из JWT (gateway ставит `X-User-Id`) — фронт просто шлёт запрос с токеном, спец. заголовки не нужны.
- Не ломать существующие контракты. Новые поля в типах — опциональные.
- Проверка после каждого пункта: `npm run build` (tsc) + `npm run lint` должны быть зелёными. Где возможно — ручная проверка флоу.
- Дизайн: соблюдать существующий стиль профиля («Оса»-редизайн), не изобретать новые паттерны. Логотип всегда жёлтый «sizbiz».
- Коммитить по одному пункту, осмысленные сообщения.

## Порядок (по возрастанию сложности)
1. Гидратация избранного (самое простое)
2. Смена пароля
3. Загрузка аватара
4. Верификация email (самое связное — типы + флоу подтверждения)

## Пункт 1 — Гидратация избранного с бэкенда 🟡→✅

**Проблема:** add/remove уже вызывают `POST/DELETE /api/v1/users/me/favorites`, но `syncWithBackend()` в `favoritesStore.ts` **определён и нигде не вызывается** → при логине избранное не подтягивается с сервера, живёт только в localStorage (на другом устройстве пусто).

**Бэкенд (готов):** `GET /api/v1/users/me/favorites` (identity `UserController`).

**Сделать (фронт):**
- Вызвать `syncWithBackend()` при старте авторизованной сессии: в `authStore` после успешного `login` и в `loadFromStorage`/инициализации, когда есть валидный токен.
- Слить серверное избранное с локальным без потери (server = источник правды для залогиненного; гость — localStorage).
- Проверить, что `GET /me/favorites` возвращает список `couponOfferId` в ожидаемом формате; при 401 (гость) — не падать.

**Файлы:** `src/store/favoritesStore.ts` (`syncWithBackend` :17,:58), `src/store/authStore.ts` (login / loadFromStorage).

**Тест:** залогиниться → избранное с сервера появилось; разлогин → остаётся гостевое из localStorage; tsc/lint зелёные.

**Проблема:** в настройках профиля нет UI смены пароля, хотя бэкенд готов.

**Бэкенд (готов):** `PUT /api/v1/auth/change-password` (identity `AuthController:95`). Сверить контракт запроса (поля `currentPassword`/`newPassword` — уточнить по `ChangePasswordRequest` в identity) и поведение (меняет `securityVersion` → возможен разлогин; проверить, не инвалидируется ли текущий токен — если да, предупредить юзера/перелогинить).

**Сделать (фронт):**
- Метод в `src/api/auth.ts`: `changePassword(currentPassword, newPassword)`.
- Форма в `components/profile/ProfileSettingsSection.tsx` (или под-компонент): текущий пароль, новый, повтор. Валидация нового пароля — **строго по правилам backend** (не ослаблять; см. как сделано в регистрации `RegisterForm`, правила уже согласованы с backend — переиспользовать).
- Обработка ошибок: неверный текущий пароль → показать ошибку поля; успех → тост + (если токен инвалидируется) корректный переход на логин.

**Файлы:** `src/api/auth.ts`, `components/profile/ProfileSettingsSection.tsx`.

**Тест:** неверный текущий → 4xx с сообщением; успешная смена → тост; правила пароля совпадают с регистрацией; tsc/lint.

## Пункт 3 — Загрузка аватара ❌→✅

**Проблема:** UI показывает только первую букву имени; `avatarUrl` уже есть в `UpdateProfileRequest`/типе юзера, но фронт его не задаёт и не рендерит.

**Бэкенд (готов):**
- `POST /api/v1/media/upload` (media, `multipart/form-data`, поле `file`, ≤20MB, требует auth) → `{ data: { fileName, url } }`, `url = /api/v1/media/{fileName}`.
- `PUT /api/v1/users/me` (identity) принимает `avatarUrl`.

**Сделать (фронт):**
- Метод в `src/api/media.ts` (создать при отсутствии): `uploadFile(file): Promise<{fileName, url}>` — `FormData`, `Content-Type` multipart (axios сам проставит boundary).
- В настройках профиля: выбор файла (input[type=file], accept `image/*`) → upload → получить `url` → `PUT /me { avatarUrl: url }` → обновить `authStore.user.avatarUrl`.
- Рендер аватара: если `avatarUrl` есть — `<img>`, иначе — текущая буква-заглушка. Места: `ProfileMobile.tsx:147`, `ProfileDesktop.tsx` (шапка профиля), и в общей шапке, если аватар там есть.
- UX: индикатор загрузки, ограничение размера/типа на клиенте (превью опц.).

**Файлы:** `src/api/media.ts` (новый), `src/api/auth.ts` (updateProfile уже есть), профильные компоненты с аватаром.

**Тест:** загрузка картинки → аватар обновился и виден после перезагрузки; не-картинка/слишком большой → понятная ошибка; tsc/lint.

## Пункт 4 — Верификация email ❌→✅

**Проблема:** `emailVerified` есть в `UserProfileResponse` (backend), но фронтовый тип `getMe`/`UserDto` его не содержит, статус не показывается, эндпоинты подтверждения не вызываются.

**Бэкенд (готов):** `POST /api/v1/auth/confirm/request` (инициировать) + `POST /api/v1/auth/confirm/email` (подтвердить). **Сверить контракт**: `confirm/email` принимает `token` (`AuthController:158-161`) — понять, приходит ли токен ссылкой на email (тогда нужен экран/маршрут `/confirm-email?token=...`) или кодом. Реализовать соответственно.

**Сделать (фронт):**
- Расширить тип пользователя: `getMe` типизировать как `UserProfileResponse` (добавить `emailVerified: boolean`, `phoneVerified: boolean`) в `src/api/auth.ts`; протянуть в `authStore.user`.
- В профиле у email — бейдж «подтверждён / не подтверждён»; если нет — кнопка «Подтвердить» → `POST /auth/confirm/request` → тост «письмо отправлено».
- Экран/маршрут подтверждения по токену из письма → `POST /auth/confirm/email { token }` → успех → обновить `emailVerified` (перезапросить `/me`).

**Файлы:** `src/api/auth.ts` (типы + методы `requestEmailConfirm`, `confirmEmail`), профиль (бейдж+кнопка), новый роут подтверждения в роутере.

**Тест:** запрос подтверждения → тост; переход по токену → статус стал «подтверждён»; tsc/lint.
