# План имплементации временного demo payment mode

## 1. Назначение документа

Этот документ описывает **временный продуктовый и технический план** для сценария покупки купона **без реальной интеграции с платёжной системой**.

Цель:

- не ждать юридического подключения `Payme` / `Click`;
- не блокировать разработку storefront, post-purchase UX и notifications;
- сохранить каноническую модель `order -> payment -> purchased coupon -> notification`;
- показать рабочий пользовательский сценарий для демо, тестирования и внутренней проверки.

Документ отвечает на вопросы:

- какой временный сценарий считаем допустимым;
- как не сломать будущую интеграцию с реальной ПС;
- что менять во frontend;
- что менять в backend;
- как обрабатывать email/SMS и “чек” / подтверждение покупки;
- как понять, что временный сценарий действительно готов.

## 2. Исходная точка

### Подтверждено кодом

В проекте уже существуют ключевые части целевого purchase flow:

- `order-service` создает `Order` и публикует `OrderCreatedEvent`;
- `payment-service` создает `Payment` после `OrderCreatedEvent`;
- `payment-service` имеет endpoint callback:
  - `POST /api/v1/payments/callback`
- `order-service` слушает `PaymentCompletedEvent` и генерирует `PurchasedCoupon`;
- `notification-service` слушает `CouponPurchasedEvent` и запускает email/SMS pipeline;
- storefront уже имеет:
  - checkout page;
  - payment page;
  - profile page с purchased coupons.

### Подтверждено кодом

Текущее ограничение:

- пользовательский payment UX предполагает внешний платёжный переход;
- реальная ПС пока не подключена;
- юридически нельзя опираться на полноценный production acquiring flow.

### Риск

- Если временно сделать shortcut вида `order -> сразу купоны`, команда сломает правильную архитектуру статусов и затем будет вынуждена переписывать flow повторно при подключении реальной ПС.

### Рекомендация

- Временное решение должно проходить **через Payment сущность и PaymentCompletedEvent**, а не мимо них.

## 3. Зафиксированные продуктовые решения

## 3.1. Стратегия на переходный период

### Подтверждено решением

- До подключения реальных `Payme` / `Click` используется **demo payment mode**.
- Реальная интеграция с ПС отложена по юридическим причинам.
- Команда не должна ждать подключения ПС для продолжения разработки purchase flow, post-purchase UX и notifications.

### Подтверждено решением

- Временный flow нужен для:
  - внутреннего тестирования;
  - демонстрации продукта;
  - доведения UX и backend orchestration;
  - проверки post-purchase цепочки.

## 3.2. Канонический временный flow

### Подтверждено решением

Временный flow должен быть таким:

1. Пользователь проходит checkout.
2. Создается `Order`.
3. Через `OrderCreatedEvent` создается `Payment` в статусе `PENDING`.
4. Пользователь попадает на payment page.
5. На payment page вместо внешнего редиректа видит блок `Демо-оплата`.
6. Нажимает `Подтвердить покупку`.
7. Backend завершает payment через специальный demo completion path.
8. Публикуется `PaymentCompletedEvent`.
9. Генерируются `PurchasedCoupon`.
10. Отправляются email/SMS уведомления.
11. Пользователь попадает в профиль / раздел покупок и видит купленные купоны.

## 3.3. Что временный flow не должен делать

### Подтверждено решением

Временный flow не должен:

- создавать купоны напрямую из checkout;
- пропускать `Payment`;
- пропускать `PaymentCompletedEvent`;
- создавать особую отдельную “демо-ветку” purchased coupons;
- ломать будущую интеграцию с реальной ПС.

## 3.4. Email / SMS / чек

### Подтверждено решением

- После успешной demo-покупки должны отрабатывать:
  - email notification;
  - SMS notification;
  - UI success confirmation.

## 3.5. Юридические и продуктовые границы demo-mode

### Подтверждено решением

Временный demo-mode нужен как **операционный и продуктовый мост** до реальной ПС, а не как альтернативная постоянная модель оплаты.

### Demo-mode должен позволять

- демонстрировать полный сценарий покупки;
- тестировать создание `Order`;
- тестировать создание `Payment`;
- тестировать выпуск `PurchasedCoupon`;
- тестировать email/SMS уведомления;
- тестировать клиентский success flow и профиль покупок.

### Demo-mode не должен обещать

- реальную банковскую транзакцию;
- реальный redirect к `Payme` / `Click`;
- юридически подтвержденный фискальный документ;
- реальный эквайринговый статус от внешнего провайдера.

### Рекомендация

Во всех пользовательских текстах временный режим должен позиционироваться как:

- `Демо-оплата`
- `Подтверждение покупки`
- `Подтверждение заказа`

И не должен позиционироваться как:

- `Фискальный чек`
- `Оплата через банк`
- `Официальный платёжный документ`

### Открытый вопрос

- Можно ли юридически и контентно называть пользовательское сообщение “чеком”, если реальный фискальный / эквайринговый документ не создается?

### Риск

- Если назвать demo-confirmation “чеком”, это может создать юридическую и продуктовую путаницу.

### Рекомендация

- До отдельного юридического подтверждения использовать формулировки:
  - `Подтверждение покупки`
  - `Подтверждение заказа`
  - `Информация о заказе`
- Не использовать wording `Фискальный чек` или аналогичную формулировку как продуктовый факт.

## 4. Целевой результат

### Рекомендация

После завершения этого плана должен работать следующий временный сценарий:

1. Пользователь оформляет заказ.
2. Попадает на payment page.
3. Видит:
   - статус подготовки платежа;
   - демо-блок подтверждения покупки.
4. Нажимает `Подтвердить покупку`.
5. Система завершает payment по канонической backend-цепочке.
6. Пользователь получает success state.
7. Пользователь видит купленные купоны в разделе покупок профиля.
8. Email/SMS отрабатывают в реальном или stub-режиме без ломания UX.

### Flow считается готовым только если

- он использует существующую payment domain model;
- он не требует реального провайдера оплаты;
- он не создает отдельную “вторую архитектуру” для demo;
- он позволяет потом безболезненно заменить demo-step на реальный redirect/callback flow.

## 5. Рекомендуемая целевая архитектура demo-mode

## 5.1. Backend model

### Рекомендация

На backend должен появиться явный режим:

- `payment.mode=demo`
- `payment.mode=provider`

### Рекомендация

В режиме `demo`:

- `Payment` все равно создается как сейчас;
- storefront-safe completion выполняется через отдельный demo endpoint;
- endpoint доступен только если backend включен в `demo mode`;
- completion path использует ту же логику, что и callback / completion chain.

### Рекомендация

В режиме `provider`:

- demo endpoint выключен;
- flow идет в реальную интеграцию ПС.

## 5.2. Demo completion contract

### Рекомендация

Для MVP demo-mode нужен отдельный endpoint, например:

- `POST /api/v1/payments/order/{orderId}/demo-complete`

Назначение:

- завершить payment без внешнего провайдера;
- использовать `orderId` как внешний идентификатор checkout flow;
- вернуть storefront-safe `PaymentResponse`.

### Рекомендация

Endpoint должен быть:

- идемпотентным;
- безопасным к повторному нажатию;
- отключаемым через конфиг;
- недоступным в production provider-mode.

## 5.3. Frontend mode

### Рекомендация

На payment page должен существовать отдельный UI-режим:

- `redirect mode`
- `demo mode`

### Рекомендация

В `demo mode` payment page показывает:

- статус заказа;
- сумму;
- пояснение, что это временная демо-оплата;
- primary CTA:
  - `Подтвердить покупку`
- secondary CTA:
  - `Вернуться в профиль`
  - или `Отменить / позже`

## 5.4. Success path

### Рекомендация

После успешной demo-confirmation:

- payment page должна перейти в `success`;
- пользователь должен увидеть:
  - что покупка подтверждена;
  - что купоны доступны в профиле;
  - что уведомление отправлено или будет отправлено;
- основной следующий шаг:
  - переход в профиль / раздел покупок.

## 5.5. Storefront ↔ payment-service contract для demo-mode

### Подтверждено кодом

Сейчас storefront уже умеет:

- читать payment по `orderId`;
- строить payment UX вокруг `GET /api/v1/payments/order/{orderId}`;
- показывать промежуточную payment page после создания заказа.

### Подтверждено кодом

Сейчас storefront **не должен** строить demo UX вокруг `paymentId`, потому что:

- стартовой точкой checkout flow является `orderId`;
- `payments.ts` уже содержит `getByOrderId(orderId)`;
- `PaymentPage` построена вокруг `orderId`, а не вокруг внутреннего `paymentId`.

### Рекомендация

Канонический контракт demo-mode:

1. `POST /api/v1/orders`
2. storefront получает `orderId`
3. storefront poll-ит `GET /api/v1/payments/order/{orderId}`
4. если backend работает в `payment.mode=demo`, payment page показывает `Демо-оплата`
5. storefront вызывает:
   - `POST /api/v1/payments/order/{orderId}/demo-complete`
6. storefront получает обновленный `PaymentResponse`
7. storefront дожидается `COMPLETED` и показывает success-state

### Риск

Если в demo-mode оставить главным контрактом `paymentId`, а не `orderId`, команда получит лишнюю развилку между текущим checkout UX и будущим production flow.

## 5.6. Что intentionally не входит во временный режим

### Подтверждено решением

Во временный demo-mode не входят:

- реальный redirect на страницу внешней ПС;
- reconciliation с внешним провайдером;
- обработка provider-specific callback payload;
- реальные платёжные ошибки банка;
- возвраты/refunds;
- частичная оплата;
- повторная оплата одного заказа через несколько провайдеров;
- юридически значимый чек.

### Следствие

Команда должна развивать только те части payment UX, которые сохранятся после подключения реальной ПС:

- ожидание создания платежа;
- подтверждение/завершение платежа;
- post-purchase success;
- профиль покупок;
- уведомления;
- статусы и ошибки.

## 6. Этапы имплементации

## Этап 0. Freeze границ demo-mode

### Цель

Зафиксировать, что demo-mode является временным, но архитектурно правильным слоем.

### Уже принято

- реальная ПС сейчас не подключается;
- нужен рабочий покупательский сценарий для демо и тестирования;
- payment domain и notifications нельзя обходить shortcut-веткой;
- после покупки пользователь должен попадать в профиль с купленными купонами.

### Exit criteria

- у команды один временный сценарий demo-payment;
- нет идеи “сразу выдавать купоны без payment”.

## Этап 1. Backend demo completion mode

### Цель

Добавить безопасный временный completion path без разрушения current payment architecture.

### Backend-задачи

1. Ввести backend flag:
   - `payment.mode=demo|provider`
2. Добавить demo completion endpoint.
3. Сделать endpoint недоступным вне demo-mode.
4. Переиспользовать существующую completion-логику:
   - обновление payment;
   - публикация `PaymentCompletedEvent`.

### Exit criteria

- backend может завершить payment в demo-mode без внешней ПС;
- completion path не дублирует бизнес-логику отдельно.

## Этап 2. Demo UX на payment page

### Цель

Сделать понятный временный клиентский flow.

### Frontend-задачи

1. На payment page определить режим:
   - demo
   - provider
2. В demo-mode показывать `Подтвердить покупку`.
3. При клике вызывать demo completion endpoint.
4. После success показывать success-state.

### Exit criteria

- пользователь может завершить покупку без реального redirect к ПС;
- UX остается похожим на будущий production flow.

## Этап 3. Post-purchase и профиль

### Цель

Показать клиенту реальный итог demo-покупки.

### Frontend-задачи

1. После success вести пользователя:
   - в профиль / раздел покупок;
   - либо оставлять на success page с CTA в профиль.
2. Убедиться, что новые купоны видны без ручных технических действий.

### Exit criteria

- после demo-покупки пользователь видит свой результат.

## Этап 4. Notifications и тексты

### Цель

Довести коммуникацию до приемлемого продукта даже без реальной ПС.

### Backend-задачи

1. Проверить, что `CouponPurchasedEvent` отрабатывает как и в основном flow.
2. Проверить email/SMS в stub или real mode.

### Content-задачи

1. Заменить ambiguous wording про “чек”, если юридически это не подтверждено.
2. Согласовать тексты:
   - success screen;
   - email subject/body;
   - SMS text.

### Exit criteria

- пользователь получает понятное подтверждение покупки;
- уведомления не ломают демо-режим.

## Этап 5. QA и switch-off plan

### Цель

Сделать временный режим безопасным и отключаемым.

### QA-задачи

1. Happy path:
   - order -> demo confirm -> purchased coupon -> profile
2. Error path:
   - повторное нажатие;
   - duplicate completion;
   - payment already completed;
   - notification failure.

### Product / Backend-задачи

1. Зафиксировать правило отключения demo-mode после реального подключения ПС.
2. Убедиться, что demo endpoint не включен в production-mode.

### Exit criteria

- временный режим работает стабильно;
- команда понимает, как его выключить при подключении реальной ПС.

## 8. Acceptance Criteria для demo-mode

### AC-001

Пользователь может пройти checkout и попасть на payment page без реальной ПС.

### AC-002

В demo-mode пользователь видит понятный CTA `Подтвердить покупку`.

После demo-confirmation payment переводится в `COMPLETED`.

`PaymentCompletedEvent` приводит к генерации purchased coupons.

## 9. Edge Cases и ожидаемое поведение

## 9.1. Повторное нажатие `Подтвердить покупку`

### Ожидаемое поведение

- повторный вызов не создает новые `PurchasedCoupon`;
- UI либо показывает уже завершенный платеж, либо возвращает безопасный success-response;
- пользователь не видит дублирования результата.

## 9.2. Payment уже завершен до открытия страницы

### Ожидаемое поведение

- `PaymentPage` должна сразу отобразить success-state;
- повторная demo-confirmation не требуется;
- пользователь может сразу перейти в профиль / покупки.

## 9.3. Demo endpoint выключен конфигом

### Ожидаемое поведение

- frontend не показывает CTA demo-confirmation;
- либо показывает понятное сообщение, что demo-оплата недоступна;
- пользователь не должен попадать в ложный тупик без объяснения.

## 9.4. Уведомление не отправилось

### Ожидаемое поведение

- успешная покупка не откатывается;
- payment и purchased coupons остаются валидными;
- ошибка логируется;
- UI success flow не ломается.

## 9.5. Купоны создались, но профиль открывается с задержкой

### Ожидаемое поведение

- success screen должен иметь CTA в профиль;
- профиль должен уметь подгрузить актуальные купоны повторным запросом;
- пользователь не должен видеть “пустую покупку” без объяснения.

## 9.6. Order найден, но Payment еще не создан

### Подтверждено кодом

Такое состояние уже возможно из-за event-driven задержки между `OrderCreatedEvent` и созданием `Payment`.

### Ожидаемое поведение

- `PaymentPage` продолжает polling;
- UI показывает промежуточное состояние подготовки платежа;
- это не считается ошибкой до достижения timeout.

## 10. Риски и ограничения

### Риск

- Если временный flow будет отличаться от будущего production flow слишком сильно, его потом придется переписывать, а не отключать.

### Риск

- Если пользовательский copy будет обещать “реальную оплату” и “чек”, это создаст недоверие и юридическую двусмысленность.

### Риск

- Если demo endpoint останется доступным в provider-mode, это будет операционный и security риск.

### Рекомендация

- Рассматривать demo-mode как временный orchestration layer для разработки и внутреннего показа, а не как постоянную продуктовую ветку.
