# Статус сквозного пользовательского флоу покупки купона

## 1. Цель документа

Этот документ отвечает на конкретный вопрос:

> Что сейчас реально происходит в пользовательском флоу  
> `зашел → посмотрел купон → добавил в корзину → пошел покупать → получил купон → получил письмо`

Документ фиксирует:

- текущий фактический статус флоу;
- какие шаги уже работают;
- где цепочка ломается;
- что нужно чинить в первую очередь;
- в каком порядке правильно добивать разработку.

## 2. Короткий ответ

### Подтверждено кодом

Сейчас этот сквозной flow **не является end-to-end рабочим**.

Корректнее описывать его статус так:

- просмотр купона — **работает**
- добавление в корзину — **частично работает**
- checkout UI — **частично работает**
- создание заказа из web checkout — **сломано / не доведено**
- автоматическое создание платежа после заказа — **не подключено**
- генерация купленного купона после успешной оплаты — **backend-часть есть**
- email/SMS уведомление о покупке — **backend-часть есть, но end-to-end flow не доведен**

### Итоговый статус

`Флоу частично реализован, но в текущем состоянии не считается рабочим E2E-сценарием.`

---

## 3. Разбор флоу по шагам

## Шаг 1. Пользователь заходит в каталог / открывает купон

### Статус

`Зеленый`

### Подтверждено кодом

Работают страницы:

- home;
- coupon catalog;
- coupon detail.

Пользователь может:

- увидеть карточки купонов;
- открыть detail page;
- прочитать условия;
- выбрать вариант покупки;
- добавить в избранное;
- нажать “в корзину” или “купить сейчас”.

### Ограничения

- часть витрины живет на fallback/mock данных;
- отзывы на coupon detail сейчас mock;
- карта в контактах использует не реальные координаты объекта.

### Вывод

- Как discovery/UI-layer этот шаг работает.

---

## Шаг 2. Пользователь добавляет купон в корзину

### Статус

`Желтый`

### Подтверждено кодом

На storefront корзина реализована в `frontend/web-app/src/store/cartStore.ts`.

Она:

- хранится в localStorage;
- умеет добавлять позиции;
- умеет менять количество;
- умеет удалять;
- показывает summary;
- открывается через drawer и отдельную страницу `/cart`.

### Подтверждено кодом

Ключ корзины формируется как:

- `couponOfferId-couponOptionId`

### Подтверждено кодом

Ограничение:

- максимум 30 позиций/единиц в корзине на фронтенде.

### Проблема

### Подтверждено кодом

Backend тоже имеет свою корзину:

- `GET /api/v1/cart`
- `POST /api/v1/cart/items`
- `DELETE /api/v1/cart/items/{id}`

Но публичный web flow в нормальном режиме использует **локальную корзину**, а не backend cart.

### Вывод

- Пользователь визуально “добавил в корзину”.
- Но это пока **frontend cart**, а не гарантированно backend checkout-ready cart.

---

## Шаг 3. Пользователь переходит в checkout

### Статус

`Желтый`

### Подтверждено кодом

Checkout page уже существует:

- `/checkout`

Есть:

- контактный шаг для гостя;
- выбор способа оплаты;
- боковой блок с заказом;
- CTA на оплату.

### Подтверждено кодом

Для гостя реализован flow:

- ввод имени;
- ввод телефона;
- `authApi.guestAuth({ phone, name })`

### Проблема

### Подтверждено кодом

После guest auth токены пишутся в localStorage вручную, но Zustand `authStore` не обновляется через `set`.

### Следствие

- На том же клиентском сеансе UI может продолжать считать пользователя неавторизованным, пока не произойдет reload или ручная загрузка из localStorage.

### Вывод

- Checkout screen как интерфейс есть.
- Но auth/checkout continuity на нем уже частично нестабильна.

---

## Шаг 4. Пользователь нажимает “оплатить” / создается заказ

### Статус

`Красный`

### Подтверждено кодом

Checkout page вызывает:

- `ordersApi.createOrder('', fullPhone)`

То есть frontend отправляет пустой email.

### Подтверждено кодом

Backend `CreateOrderRequest` требует:

- `email` — обязательный, `@NotBlank`, `@Email`
- `phone` — обязательный

### Следствие

- Web checkout в текущем коде должен падать на валидации backend при попытке создать заказ.

### Дополнительная проблема

### Подтверждено кодом

`OrderService.createOrder()` строит заказ из **backend корзины**, а не из localStorage storefront-корзины.

### Следствие

Даже если бы email был валиден:

- заказ все равно не совпадал бы с тем, что пользователь собрал на storefront, если frontend cart не синхронизирован с backend cart.

### Вывод

- На этом шаге flow сейчас фактически ломается.

---

## Шаг 5. После создания заказа должен появиться платеж

### Статус

`Красный`

### Подтверждено кодом

`order-service` после создания заказа публикует:

- `OrderCreatedEvent`

в:

- exchange `order.exchange`
- routing key `order.created`

### Подтверждено кодом

`payment-service` действительно имеет `PaymentService.createPayment(...)`, и комментарии говорят, что он “должен вызываться по OrderCreatedEvent”.

### Подтверждено кодом

Но в `payment-service` **не найден**:

- listener на `OrderCreatedEvent`;
- queue/binding для `order.created`;
- `@RabbitListener` на этот event.

### Следствие

- Автоматическая цепочка `order created → payment created` сейчас не собрана.

### Вывод

- Даже если заказ будет создан, платёж автоматически не подхватится event-driven flow, как это подразумевается архитектурой.

---

## Шаг 6. Оплата должна завершиться и сгенерировать purchased coupons

### Статус

`Желтый`

### Подтверждено кодом

`payment-service` умеет:

- создать `Payment` со статусом `PENDING`
- обработать callback
- перевести платеж в `COMPLETED`
- опубликовать `PaymentCompletedEvent`

### Подтверждено кодом

`order-service` имеет listener:

- `PaymentEventListener`

который слушает:

- `payment.completed.queue`

и вызывает:

- `orderService.generatePurchasedCoupons(orderId)`

### Подтверждено кодом

`generatePurchasedCoupons(...)`:

- переводит order в `PAID`;
- создает `PurchasedCoupon`;
- генерирует `couponCode`;
- генерирует `qrToken`;
- публикует `CouponPurchasedEvent`.

### Ограничение

- Эта часть работает **только если** платеж уже дошел до callback или кто-то явно вызвал payment completion.

### Вывод

- Backend-фундамент этого шага есть.
- Но он не включается из storefront автоматически из-за проблем выше.

---

## Шаг 7. Пользователь получает купленный купон в профиле

### Статус

`Желтый`

### Подтверждено кодом

Profile page запрашивает:

- `GET /api/v1/orders/my-coupons`

по статусам:

- `ACTIVE`
- `USED`
- `EXPIRED`

### Подтверждено кодом

Если purchased coupons сгенерированы, backend умеет их отдать.

### Проблема

### Подтверждено кодом

После guest auth checkout пишет токены в localStorage, но не обновляет authStore.

### Следствие

- После успешного checkout и `navigate('/profile')` пользователь может увидеть гостевой empty state вместо реального профиля, пока приложение не перезагрузится.

### Вывод

- Backend-часть профиля есть.
- User-facing continuity после checkout сейчас ненадежна.

---

## Шаг 8. Пользователю приходит письмо / SMS / уведомление

### Статус

`Желтый`

### Подтверждено кодом

После генерации purchased coupons `order-service` публикует:

- `CouponPurchasedEvent`

### Подтверждено кодом

`notification-service` слушает:

- `coupon.purchased.queue`

и вызывает:

- `EmailService.sendCouponPurchasedEmail(...)`
- `SmsService.sendCouponPurchasedSms(...)`

### Подтверждено кодом

Также есть in-app notification infrastructure, но именно purchase email/SMS идут через `CouponPurchasedListener`.

### Ограничение 1

### Подтверждено кодом

Email/SMS реально уйдут только если:

1. заказ создан;
2. платеж завершен;
3. purchased coupons сгенерированы;
4. `CouponPurchasedEvent` дошел;
5. отправка уведомлений включена конфигом, а не работает в stub mode.

### Ограничение 2

### Подтверждено кодом

Order creation сейчас ожидает валидный email и phone.

Но публичный checkout передает пустой email.

### Следствие

- Даже слой уведомлений зависит от починки более ранних шагов.

### Вывод

- Сам notification pipeline в backend существует.
- Но как часть реального пользовательского E2E flow он сейчас не считается рабочим.

## 5. Главные точки разрыва

## 5.1. Checkout отправляет невалидный payload

### Подтверждено кодом

- frontend отправляет пустой email;
- backend требует обязательный email.

## 5.2. Frontend cart и backend cart не совпадают

### Подтверждено кодом

- storefront работает на local cart;
- backend order создается из server cart.

## 5.3. Нет автоматического слушателя `OrderCreatedEvent` в payment-service

### Подтверждено кодом

- архитектура подразумевает этот шаг;
- реализация слушателя отсутствует.

## 5.4. Auth continuity после guest checkout не завершена

### Подтверждено кодом

- localStorage обновляется;
- Zustand authStore не обновляется.

## 5.5. Notification pipeline зависит от upstream шагов

### Подтверждено кодом

- Email/SMS существуют как downstream эффект, но upstream цепочка из storefront не доведена.

## 6. Правильный вывод по текущему состоянию

### Подтверждено кодом

Если ответить очень честно:

> Пользовательский flow  
> `посмотрел купон → добавил в корзину → купил → получил купон → получил письмо`  
> сейчас **не готов как рабочий production flow**.

### Более точная формулировка

- `browse` готов;
- `cart UX` готов частично;
- `checkout UI` готов частично;
- `order/payment integration` не доведена;
- `post-payment backend foundation` существует;
- `notification backend foundation` существует.

## 7. Что нужно исправлять в первую очередь

## Приоритет 1. Собрать один канонический checkout flow

### Рекомендация

Сначала принять решение:

- либо storefront использует backend cart;
- либо storefront делает direct-buy/direct-order flow без серверной корзины.

Без этого дальше чинить checkout бессмысленно.

## Приоритет 2. Исправить contract создания заказа

### Рекомендация

Нужно согласовать:

- какие поля обязательны для checkout;
- откуда берется email;
- возможен ли guest checkout без email;
- как заполняются контакты для уведомлений.

## Приоритет 3. Довести payment orchestration

### Рекомендация

Нужно явно собрать цепочку:

- `OrderCreatedEvent` → `Payment`
- пользователь уходит по `paymentUrl` или внутри provider flow
- callback завершает payment
- `PaymentCompletedEvent` генерирует purchased coupons

## Приоритет 4. Починить auth continuity после guest checkout

### Рекомендация

После guest auth storefront должен находиться в консистентном “logged-in as guest” состоянии, а не только иметь токен в localStorage.

## Приоритет 5. Только потом шлифовать profile/email UX

### Рекомендация

- После стабилизации order/payment chain уже имеет смысл добивать:
  - корректный профиль после покупки;
  - письмо;
  - SMS;
  - QR UX;
  - refund UX.

---

## 8. Как использовать этот документ дальше

### Рекомендация

Дальше этот flow надо превратить в рабочий delivery-plan из трех частей:

1. `Flow decision`
   - фиксируем каноническую модель cart/checkout/payment.

2. `Flow repair`
   - приводим frontend и backend к одному контракту.

3. `Flow completion`
   - добиваем профиль, письма, QR, ошибки, edge cases.
