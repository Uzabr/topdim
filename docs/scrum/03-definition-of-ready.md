# 03. Definition of Ready (DoR)

> **Смысл:** DoR защищает спринт от задач, которые команда физически не сможет закончить,
> потому что не хватает информации, решения или доступа.
> **Правило:** задача, не проходящая DoR, **не попадает в Sprint Planning**. Не «возьмём и разберёмся» — не берём.
> **Проверяет:** Scrum Master на груминге. **Готовит:** Product Owner при поддержке команды.

DoR — это не бюрократия и не способ заблокировать работу. Это ответ на вопрос: «если мы возьмём это
в понедельник, сможем ли мы к концу спринта показать результат?»

---

## 1. Базовый DoR — для любой задачи

- [ ] **Есть ценность.** Понятно, чью проблему решаем и зачем. Для user story — заполнен формат
      «Как <роль>, я хочу <действие>, чтобы <ценность>».
- [ ] **Заголовок конкретный.** «Починить каталог» — не проходит. «Каталог не применяет `categoryId` из URL» — проходит.
- [ ] **Привязка к проекту-milestone** в Linear и к эпику.
- [ ] **Критерии приёмки (AC)** сформулированы и проверяемы. Минимум: happy path + один негативный случай.
- [ ] **Оценка** проставлена командой в story points.
- [ ] **Нет неснятых внешних блокеров.** Все зависимости либо закрыты, либо запланированы раньше в этом же спринте.
- [ ] **Приоритет** выставлен PO.
- [ ] **Помещается в спринт.** Если команда считает, что задача больше 8 SP — она разбивается.

---

## 2. Дополнительно для backend-историй (Java / Spring)

- [ ] Указан **затрагиваемый сервис** (identity / coupon / order / payment / bazaar / notification / media /
      api-gateway / discovery-server / config-server).
- [ ] Если меняется **публичный API** — контракт описан явно: метод, путь, request/response DTO, коды ответов.
      Изменение существующего контракта помечено как breaking или non-breaking.
- [ ] Если нужна **миграция БД** — описано, что меняется, обратима ли миграция, есть ли риск блокировки таблицы.
- [ ] Указано, **пересекает ли задача границы сервисов**. Если да — выбран способ взаимодействия
      (REST/Feign, событие через RabbitMQ) и обоснован. Прямой доступ к чужой БД запрещён
      (`.claude/rules/microservices.md`).
- [ ] Для операций с деньгами, остатками, погашением — явно описаны требования к **идемпотентности и конкурентности**.
- [ ] Понятно, какие **транзакционные границы** затрагиваются.

## 3. Дополнительно для frontend-историй

- [ ] Указано приложение: `web-app` (sizbiz.uz) / `admin-app` / `partner` (каталог `frontend/partner`,
      лейбл `area/partner-app`).
- [ ] Есть макет, ссылка на существующий экран или текстовое описание всех состояний:
      **loading, empty, error, success**.
- [ ] Известно, какие API-эндпоинты используются и существуют ли они уже. Если поля нет на бэкенде —
      создана связанная backend-задача.
- [ ] Описано поведение для роли `GUEST`, если экран доступен без авторизации.
- [ ] Указаны требования локализации: минимум `ru` и `uz` (PRD §27).

## 4. Дополнительно для security-историй

- [ ] Есть ссылка на источник: пункт из `docs/SECURITY_HARDENING.md`, находка пентеста или CVE.
- [ ] **Описан сценарий атаки** — что именно может сделать злоумышленник сейчас.
- [ ] Описан способ проверки исправления (как убедиться, что дыра закрыта).
- [ ] Оценено влияние на существующих пользователей (например: инвалидация сессий, принудительный релогин).
- [ ] Понятно, требуется ли ротация секретов после исправления.

## 5. Дополнительно для инфраструктурных историй

- [ ] Описано влияние на деплой и на production-стенд.
- [ ] Есть план отката.
- [ ] Указано, нужен ли простой сервиса и какой.
- [ ] Проверено влияние на бэкапы и на восстановление.

## 6. Дополнительно для багов

- [ ] **Шаги воспроизведения** — по пунктам, воспроизводимо.
- [ ] Ожидаемое и фактическое поведение.
- [ ] Окружение: production / staging / локально; браузер или клиент; роль пользователя.
- [ ] Severity выставлена по шкале из [06-workflow-and-estimation.md](06-workflow-and-estimation.md).
- [ ] Логи, скриншот, correlation ID — если доступны. **Без секретов и персональных данных.**

## 7. Дополнительно для спайков (исследований)

- [ ] Сформулирован **вопрос**, на который спайк отвечает.
- [ ] Задан **таймбокс** в часах или SP. Спайк без таймбокса — не спайк.
- [ ] Указано, каким артефактом закончится: ADR, документ, прототип, ответ в комментарии.
- [ ] Понятно, какое решение будет принято на основе результата.

---

## 8. Как это работает на практике

**Backlog Refinement (груминг)** — **дважды за спринт** (по одному разу в неделю), ~60 минут.
PO приносит истории верхней части backlog,
команда задаёт вопросы, SM проверяет по чек-листу. Цель — иметь готовыми **истории минимум на 1.5 спринта вперёд**.

Статусы в Linear:

- `Backlog` — идея, DoR не проверялся.
- `Todo` — **прошла DoR**, может быть взята в цикл.
- `Blocked` — не проходит DoR из-за внешнего решения или зависимости.

Если на планировании выясняется, что история на самом деле не готова — она возвращается в `Backlog`,
а не берётся «под честное слово». Это ответственность SM.

---

## 9. Осознанное исключение

DoR можно нарушить **только** для инцидентов production severity `S1`/`S2`. Такая задача создаётся сразу
в `In Progress` с лейблом `incident`, а недостающая документация дописывается после стабилизации.
Все прочие исключения обсуждаются на ретроспективе как сигнал проблемы процесса.
