## 1. Что такое SizBiz

**SizBiz** — платформа локальных купонов и скидок для рынка Узбекистана (старт — Ташкент), объединяющая
два контура:

1. **Купонный маркетплейс** — пользователь находит оффер, покупает купон, получает PIN/QR и погашает его у мерчанта.
2. **Онлайн-справочник базаров** — каталог базаров и магазинов с картой (2GIS), навигация к офферам через физическую географию рынка.

Технический монорепозиторий и внутренние идентификаторы носят кодовое имя `topdim` — это **не бренд**
и не должно попадать в пользовательские интерфейсы, презентации и задачи Linear.

**Публичные поверхности:**

| Поверхность | Домен | Аудитория |
|---|---|---|
| Storefront (web-app) | `sizbiz.uz` | Покупатели, гости |
| API Gateway | `api.sizbiz.uz` | Все клиенты |
| Админ-панель | `admin.sizbiz.uz` | Модераторы, админы, супер-админы |
| Кабинет партнёра | `partner.sizbiz.uz` | Мерчанты, кассиры |
| Telegram-бот | — | Лиды мерчантов, операционка |

## 2. Зачем существует проект

### 2.1. Проблема пользователя

Локальные скидки на узбекском рынке живут в разрозненных Telegram-каналах, Instagram-сторис и офлайн-вывесках.
Условия оффера непрозрачны: неясно, действует ли акция сегодня, у какого именно продавца и что именно входит в цену.
Пользователь не может доверять предложению до того, как физически придёт в точку.

### 2.2. Проблема мерчанта

Мелкий и средний продавец на базаре не имеет канала продвижения, кроме потока мимо прилавка. Запуск акции
требует либо дорогой рекламы, либо ручной работы в мессенджерах без контроля результата. Нет данных о том,
сработала акция или нет.

### 2.3. Проблема платформы

Без единого жизненного цикла оффера (лид → черновик → согласование с мерчантом → публикация → продажа →
погашение) невозможно гарантировать качество карточек и предотвращать конфликты между storefront,
админкой и bot-flow.

## 3. Цели проекта

### 3.1. Бизнес-цели

| Цель | Как проверяем |
|---|---|
| Сформировать управляемую платформу локальных офферов | Единый lifecycle купона работает end-to-end без ручных обходов |
| Увеличить число опубликованных и реально использованных акций | Рост числа `ACTIVE` купонов и redemption rate по спринтам |
| Упростить привлечение мерчантов без потери контроля качества | Сокращение времени `lead → active coupon` |
| Получить измеримую воронку | Дашборд: просмотр → сохранение → покупка → погашение |

### 3.2. Цели пользователя

- Быстро находить выгодные локальные предложения.
- Понимать условия оффера без скрытых допущений.
- Доверять карточке и контексту мерчанта.
- Удобно хранить и предъявлять купленные купоны.

### 3.3. Цели мерчанта

- Подать заявку и запустить оффер быстро.
- Понимать статус публикации в любой момент.
- Согласовывать карточку без сложного кабинета на MVP.
- Видеть базовую статистику по результатам акции.

### 3.4. Платформенные и операционные цели

- Единый жизненный цикл сущностей, ясные роли и права.
- Исключить противоречия между storefront, админкой, bot-flow и backend-правилами.
- Снизить количество решений «на словах» у операционной команды.
- Сделать статусы, visibility и edge cases тестируемыми.

## 4. Метрики успеха

### 4.1. Продуктовые метрики (владелец — PO)

**Воронка покупки:** просмотры карточки купона → CTR карточка→деталь → add to favorites → add to cart →
checkout start → order creation → payment success → **redemption rate**.

**Качество и доверие:** refund rate, review creation rate, доля жалоб на купон.

**Discovery:** использование поиска в справочнике, использование выбора области на карте, CTR базар→магазин.

**Мерчантская воронка:** объём лидов, конверсия лид → активный купон, время цикла модерации,
доля возвратов карточки на доработку (revision rate), sold-out rate.

### 4.2. Метрики процесса (владелец — Scrum Master)

Sprint goal achievement rate, velocity и её стабильность, доля незапланированной работы,
carryover rate, cycle time, escaped defects. Детали — в [10-metrics-and-reporting.md](10-metrics-and-reporting.md).

### 4.3. Метрики надёжности (владелец — Delivery Manager)

Доступность `api.sizbiz.uz`, p95 latency ключевых эндпоинтов, доля неуспешных деплоев,
время восстановления, возраст последнего проверенного бэкапа.

> ⚠️ Формальные SLO/SLI, RTO и RPO **ещё не зафиксированы** — это открытый пробел GAP-01
> (`docs/ru/20-documentation-gaps.md`). Пока метрики надёжности отслеживаются как наблюдения, не как обязательства.

## 5. Границы проекта

### 5.1. В зоне ответственности команды

Backend-микросервисы (identity, coupon, order, payment, bazaar, notification, media),
инфраструктура (api-gateway, discovery-server, config-server), три фронтенд-приложения, Telegram-бот,
CI/CD, эксплуатация production-стенда, документация.

### 5.2. Non-goals MVP

Прямая цитата из PRD §4 — эти вещи **не считаются обязательными** для MVP:

- Полноценный self-service кабинет мерчанта уровня зрелого SaaS.
- Универсальный e-commerce маркетплейс с логистикой.
- Глубокая CRM для мерчантов.
- Сложная social/community-платформа с UGC сверх отзывов.
- Multi-city enterprise-раскатка без закреплённых правил видимости по городу.
- Полная замена внешних картографических систем собственным GIS.

> **Важный риск из PRD:** в коде уже заложены элементы будущих модулей. Наличие кода в репозитории
> **не означает**, что функциональность входит в MVP. Каждая такая находка требует явного продуктового решения.

### 5.3. Post-MVP

Публичные страницы мерчанта, self-service создание/редактирование офферов, полноценный notification center,
расширенный workflow жалоб, кластеризация на карте, city-aware каталог, ранжирование поиска и подсказки,
UI отзывов на storefront, богатые backoffice-панели, консолидация canonical bazaar-домена.

## 8. Ключевые риски проекта

| Риск | Влияние | Митигация |
|---|---|---|
| **Oversell:** резервирование остатка неатомарно, два покупателя могут купить последний купон | Прямые финансовые и репутационные потери | P0-история в первом спринте, интеграционный тест на конкурентную покупку |
| **Ключ 2GIS в публичном бандле** | Компрометация внешнего ключа, счёт за чужой трафик | Backend-прокси + отзыв ключа, P0 |
| **Платежи только в demo-режиме** | Нет реальной выручки | Определить провайдера (Q8), затем эпик интеграции |
| **Фронтенд-тесты есть, но CI их не запускает** (`web-app` — 22 Vitest-файла, job `frontend` в `ci.yml` выполняет только lint и build; в `admin-app` и `partner` тестов нет вовсе) | Регрессии в checkout/refund проходят незаметно | Эпик тест-автоматизации, запуск тестов в CI, порог покрытия растёт по спринтам |
| **PRD отстаёт от кода примерно на 7 недель** (обновлён 2026-06-08) | Команда принимает решения по устаревшему источнику | Эпик «Документация как источник правды», PRD обновляется в конце каждого спринта |
| **История компрометации сервера** (июнь 2026, майнер + руткит) | Повторный инцидент | Хардненинг закрыт, но нужны мониторинг и регулярный аудит; см. `docs/SERVER_SECURITY_PLAN.md` |
| **Расхождение статусов между документами** (PROJECT_STATE vs SECURITY_HARDENING по пунктам M1/M4/M5/M6, N-C2, N-M1) и между документами и кодом (часть пунктов уже закрыта в коде, но помечена открытой) | Работа делается дважды или не делается вовсе | Верификация по коду перед постановкой в спринт (спайки S03.1 и E-09 в спринте 1) |
