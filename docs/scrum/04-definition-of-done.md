# 04. Definition of Done (DoD)

> **Смысл:** DoD — единое и **бинарное** определение готовности. Задача либо соответствует всем пунктам,
> либо не готова. «Готово на 90%» не существует.
> **Область действия:** DoD применяется к каждой задаче, а не только к спринту в целом.
> **Владелец:** команда разработки. **Контролирует соблюдение:** Scrum Master.

DoD у SizBiz строже обычного по двум причинам: продукт работает с деньгами (покупка и погашение купонов),
и сервер уже был скомпрометирован в июне 2026. Ошибка в безопасности здесь — не теоретический риск.

---

## 1. Базовый DoD — обязателен для всех задач

### Код

- [ ] Код написан, соответствует правилам проекта (`CLAUDE.md`, `.claude/rules/`).
- [ ] Нет закомментированного мёртвого кода и отладочных `System.out` / `console.log`.
- [ ] Нет захардкоженных секретов, ключей, токенов, паролей. `gitleaks` в pre-commit проходит.
- [ ] Нет TODO без созданной задачи в Linear (в комментарии — ссылка на issue).

### Ревью

- [ ] Pull Request создан, описание объясняет **что** и **зачем**, со ссылкой на issue Linear.
- [ ] Минимум **один апрув** от другого разработчика, который реально прочитал дифф.
- [ ] Для изменений в auth, платежах, заказах, погашении, gateway — **обязательный второй ревьюер**.
- [ ] Все замечания ревью закрыты или вынесены в отдельные задачи.

### Тесты

- [ ] Написаны тесты на новую или изменённую бизнес-логику.
- [ ] Покрыты негативные сценарии из `.claude/rules/testing.md`: невалидный ввод, отсутствующая сущность,
      отказ в доступе, дублирующий запрос, истёкшее состояние, уже обработанное состояние, откат транзакции.
- [ ] Полная сборка `./gradlew build` проходит локально.
- [ ] CI зелёный.

### Документация

- [ ] Изменение публичного API отражено в OpenAPI/Swagger.
- [ ] Затронутые документы обновлены: `docs/PROJECT_STATE.md` при изменении инфраструктуры/архитектуры,
      `docs/product/prd.md` при изменении продуктового поведения, соответствующий раздел `docs/ru/`.
- [ ] Архитектурное решение зафиксировано ADR в `docs/ru/adr/`.

### Подтверждение результата

- [ ] Все критерии приёмки задачи выполнены и проверены.
- [ ] Для user story PO подтвердил соответствие критериям приёмки.
- [ ] Изменение задеплоено или готово к деплою без ручных недокументированных шагов.
- [ ] Статус в Linear обновлён, время и решение зафиксированы.

## 2. Дополнительно для backend (Java / Spring Boot)

- [ ] Контроллер тонкий, бизнес-логика в сервисном слое.
- [ ] JPA-сущности **не отдаются наружу** — только DTO.
- [ ] Входящие DTO валидируются через Jakarta Validation.
- [ ] Транзакционные границы заданы осознанно, не «по умолчанию».
- [ ] Проверено отсутствие N+1 запросов и проблем ленивой загрузки.
- [ ] Нет широкого `catch (Exception e)` без явного обоснования.
- [ ] Конструкторное внедрение зависимостей.
- [ ] Для операций с остатками и деньгами — доказана **атомарность и идемпотентность**
      (пессимистичная блокировка, `@Version` или атомарный SQL `UPDATE`), есть тест на конкурентный доступ.
- [ ] Миграция Flyway обратима или явно описано, почему нет. Влияние на существующие данные проверено.
- [ ] Для часто фильтруемых колонок рассмотрены индексы.
- [ ] Actuator health сервиса остаётся `UP` после изменения.

## 3. Дополнительно для межсервисных изменений

- [ ] Границы сервисов не нарушены, прямого доступа к чужой БД нет.
- [ ] Для событий описано поведение при дубликате, при переупорядочивании и при потере сообщения.
- [ ] Изменение публичного контракта явно помечено и согласовано с потребителями.
- [ ] Правила gateway не раскрывают внутренние детали сервисов.

## 4. Дополнительно для frontend

- [ ] Реализованы все состояния: loading, empty, error, success — и они **правдивы**
      (не показываем «пусто», когда на самом деле ошибка).
- [ ] Проверено на мобильном разрешении и на десктопе.
- [ ] Базовая доступность: aria-labels на интерактивных элементах, работа с клавиатуры, фокус в модалках.
- [ ] Строки локализованы (`ru`, `uz`), нет захардкоженного текста в компонентах.
- [ ] Ошибки API обрабатываются мягко, стектрейсы не показываются пользователю.
- [ ] Бренд в интерфейсе — **SizBiz**; строка `topdim` не встречается в пользовательском тексте.
- [ ] Секреты и API-ключи не попадают в бандл (проверка: `grep` по собранному бандлу).

## 5. Дополнительно для security-задач

- [ ] Уязвимость закрыта и **проверена тем же способом, которым была найдена**.
- [ ] Проверены смежные векторы, а не только конкретный найденный путь.
- [ ] Ошибки не раскрывают лишнее: нет user enumeration, нет утечки внутренних деталей в сообщениях.
- [ ] Права проверяются на бэкенде, а не только скрытием элементов в UI.
- [ ] Изменения auth-логики покрыты тестами: логин, refresh, logout, истёкший токен, невалидный токен, отозванный токен.
- [ ] Соответствующий пункт в `docs/SECURITY_HARDENING.md` обновлён с датой и способом верификации.
- [ ] **Безопасность не ослаблена ради прохождения тестов** (`.claude/rules/security.md`).

## 6. Дополнительно для инфраструктуры и деплоя

- [ ] Изменение отражено в `docker-compose.yml` / `docker-compose.prod.yml` / CI-конфигурации.
- [ ] Задокументированы новые переменные окружения (имена — да, значения — нет).
- [ ] Проверено, что healthcheck и `SERVER_PORT` сервиса согласованы.
- [ ] План отката описан и выполним.
- [ ] Влияние на бэкапы проверено; если появилась новая БД — она включена в бэкап-скрипт.
- [ ] Изменение отражено в `docs/PROJECT_STATE.md`.

## 7. Definition of Done для спринта

Спринт считается завершённым, когда:

- [ ] Все задачи спринта либо соответствуют DoD, либо явно возвращены в backlog с указанием причины.
- [ ] Инкремент работоспособен и не ломает существующую функциональность.
- [ ] Sprint Goal достигнут или зафиксирована причина недостижения.
- [ ] Sprint Review проведён, инкремент проинспектирован, backlog адаптирован.
- [ ] Ретроспектива проведена, action items созданы как задачи в Linear с владельцем и сроком.
- [ ] Метрики спринта обновлены ([10-metrics-and-reporting.md](10-metrics-and-reporting.md)).
- [ ] `docs/PROJECT_STATE.md` актуален.

## 8. Долг DoD

Если задачу закрывают без выполнения части DoD (например, тесты откладываются) — это **явное решение команды**,
которое:

1. Фиксируется комментарием в issue с причиной.
2. Порождает связанную задачу с лейблом `dod-debt` и приоритетом не ниже `High`.
3. Разбирается на ближайшей ретроспективе.

Три и более случая `dod-debt` за спринт — сигнал, что либо DoD нереалистичен, либо команда перегружена.
И то, и другое обсуждается на ретро, а не игнорируется.

---

## 9. Эволюция DoD

DoD пересматривается на ретроспективе **раз в 3 спринта**. Направление изменений — ужесточение по мере
роста зрелости. Ближайшие плановые ужесточения:

| Когда | Что добавляем |
|---|---|
| После эпика тест-автоматизации | Порог покрытия backend поднимается с 10% до 40%, затем до 60% |
| После запуска тестов фронта в CI | Обязательные unit-тесты для новых frontend-компонентов во всех трёх SPA |
| После внедрения Playwright | Прогон e2e-сценария покупки перед релизом |
| После настройки трейсинга | Обязательный correlation ID в логах новых эндпоинтов |
| После внедрения SBOM/vuln scan | Отсутствие критических уязвимостей в образе |
