# 09. Шаблоны

> Шаблоны 1–4 заводятся в Linear (Settings → Teams → SizBiz → Templates).
> Шаблоны 5–8 используются как заготовки документов и сообщений.

---

## 1. User Story (шаблон Linear)

```markdown
## История
Как <роль: покупатель / мерчант / модератор / админ / инженер>,
я хочу <действие>,
чтобы <ценность>.

## Контекст
<Почему сейчас. Ссылки на PRD, аудит, обращение пользователя.>

## Критерии приёмки
- [ ] Happy path: <ожидаемое поведение>
- [ ] Негативный случай: <невалидный ввод / нет прав / состояние уже обработано>
- [ ] Edge case: <граничное условие>

## Технические заметки
- Затрагиваемые сервисы:
- Изменение публичного API: да / нет (если да — контракт ниже)
- Миграция БД: да / нет (обратима?)
- Пересечение границ сервисов: нет / REST / событие

## Definition of Ready
- [ ] Ценность понятна
- [ ] AC проверяемы
- [ ] Оценка проставлена
- [ ] Внешних блокеров нет
- [ ] Помещается в спринт

## Definition of Done
- [ ] Код + тесты, включая негативные
- [ ] PR отревьюен (для auth/платежей/заказов — двумя ревьюерами)
- [ ] CI зелёный
- [ ] Документация обновлена
- [ ] PO подтвердил соответствие критериям приёмки
```

## 3. Tech Debt (шаблон Linear)

```markdown
## Риск для production
<Что может сломаться и с какими последствиями. Не "некрасивый код", а конкретный риск.>

## Текущее поведение
<Как устроено сейчас, со ссылками на файлы и строки.>

## Предлагаемое решение
<Варианты с плюсами и минусами, если их несколько.>

## Цена бездействия
<Что будет, если не делать: растёт ли риск со временем.>

## Влияние на существующее
- Обратная совместимость:
- Требуется ли миграция:
- Требуется ли простой:
```

## Критерий завершения

## 5. Sprint Goal

Формулируется как **изменение состояния**, а не как список работ.

```
Спринт <N> (<даты>)

Цель: <одно предложение — что изменится к концу спринта>

Почему это важно сейчас: <1–2 предложения>

Как поймём, что достигли:
- <проверяемый признак 1>
- <проверяемый признак 2>
```

**Хорошие примеры:**

- «Купить купон, которого нет в наличии, стало невозможно — и это доказано автотестом на конкурентную покупку.»
- «Ключ 2GIS больше не доступен из публичного бандла, старый ключ отозван.»
- «Все сервисы, включая bazaar-service, доставляются в production автоматически.»

**Плохие примеры:**

- «Закрыть 12 задач.» — это не цель, а объём.
- «Работать над безопасностью.» — не проверяемо.

## 6. Ретроспектива — протокол

```markdown
# Ретроспектива — спринт <N>, <дата>

## Факты
- Sprint Goal: достигнут / достигнут частично / не достигнут
- Запланировано: <SP> · Завершено: <SP> · Перенесено: <SP>
- Незапланированная работа: <SP> (<%>)
- Escaped defects: <кол-во>
- Инциденты: <кол-во, severity>

## Проверка прошлых action items
| Action item | Владелец | Статус |
|---|---|---|

## Что обсудили
### Хорошо работает
### Мешает
### Идеи

## Action items (максимум 3)
| Что | Владелец | Срок | Issue |
|---|---|---|---|

## Настроение команды
<1–5 или короткие реплики>
```

## 7. Постмортем инцидента (безвиновный)

Обязателен для `S1` в течение 48 часов после устранения.

```markdown
# Постмортем: <краткое описание>

**Дата:** · **Длительность:** · **Severity:** · **Автор:**

## Влияние
<Кто пострадал, сколько, что именно не работало. По возможности — цифры.>

## Хронология (время в Asia/Tashkent)
| Время | Событие |
|---|---|
| | Начало влияния |
| | Обнаружено (как?) |
| | Начата диагностика |
| | Найдена причина |
| | Применено исправление |
| | Влияние прекратилось |

## Первопричина
<Техническая причина. Без имён и обвинений — ищем причину в системе, а не в человеке.>

## Что сработало хорошо

## Что сработало плохо

## Где нам повезло
<Что могло сделать инцидент хуже, но случайно не сделало. Это будущие риски.>

## Действия
| Действие | Тип (предотвратить / обнаружить / смягчить) | Владелец | Issue |
|---|---|---|---|
```

**Принцип:** ищем сбой процесса или системы, а не виноватого. Человек, нажавший кнопку, — не причина;
причина в том, что систему можно было сломать нажатием кнопки.

## 8. Обновление для стейкхолдеров

Отправляет PO или Delivery Manager после Sprint Review, раз в 2 недели.

```markdown
# SizBiz — итоги спринта <N> (<даты>)

## Коротко
<2–3 предложения: что стало возможно для пользователей или насколько система стала надёжнее.>

## Что сделано
- <результат, а не задача: "покупка последнего купона больше не приводит к отказу после оплаты">
- <...>

## Что не успели и почему
- <честно, с причиной>

## Риски и решения, которые нужны от бизнеса
- <например: нужен выбор платёжного провайдера — блокирует эпик платежей>

## Следующий спринт
Цель: <sprint goal следующего спринта>
```

> **Правило:** пишем на языке результата, а не задач. Стейкхолдеру важно «что теперь можно», а не «сколько тикетов закрыли».
> Бренд в письме — **SizBiz**, не `topdim`.

## 9. Daily-заметка (для асинхронного формата)

```
По задачам, а не по людям.

SIZ-123 Атомарное резервирование остатка
  вчера: реализована пессимистичная блокировка
  сегодня: тест на конкурентную покупку
  мешает: —

SIZ-140 Прокси 2GIS
  вчера: —
  сегодня: не начинал, жду доступ к кабинету 2GIS
  мешает: ⚠️ доступ к кабинету 2GIS (SM, второй день)

К цели спринта: движемся, риск по SIZ-140.
```
