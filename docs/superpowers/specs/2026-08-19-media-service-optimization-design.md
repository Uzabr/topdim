# Media-service: оптимизация хранения и отдачи — дизайн

**Дата:** 2026-08-19
**Ветка:** `feat/media-service-optimization`
**Статус:** дизайн утверждён, готов к плану реализации

## 1. Проблема и цель

**Сейчас** media-service кладёт загруженные файлы в MinIO «как есть» (без сжатия/ресайза),
а на отдаче возвращает `byte[]` c `Content-Type: application/octet-stream`, читая весь файл в
память (`readAllBytes`) и без заголовков кэша. В зависимостях нет ни одной image-либы. Итог:
диск занимают тяжёлые оригиналы, отдача медленная и не кэшируется, картинки грузятся в полном
размере даже в мелкие слоты.

Параллельно на проде загрузка вообще не работает: nginx режет тело дефолтным `client_max_body_size`
1MB → **413** для фото >1MB (диагностика — [[topdim-merchant-logo-upload]]).

**Цель:** принимаем картинку → отдаём лёгкую и визуально-безупречную → диск занимаем минимально.

## 2. Выбранная стратегия (обсуждено и утверждено)

**Вариант «оптимизировать при загрузке, тяжёлый оригинал не хранить».**
Причины выбора под наш контекст: приоритет — экономия диска; медиа простые (логотипы, обложки,
фото купонов), пиксель-в-пиксель оригинал не нужен; минимум инфраструктуры (библиотека внутри
существующего сервиса, без нового imgproxy-контейнера).

**Ключевые решения:**
- Формат отдачи — **WebP-only**, качество **q≈82** (визуально без потерь, ~25–35% легче JPEG).
  AVIF отложен (дороже по CPU, сложнее в Java).
- **3 размера** при загрузке (WebP), по длинной стороне, **без апскейла**:
  `thumb ~200px` (лого/иконка/аватар), `card ~600px` (обложки в списках), `full ≤1600px` (детально/баннеры).
- **Стрип EXIF/метаданных** (легче + приватность).
- **413** чиним подъёмом nginx `client_max_body_size` до `20m` (синхронный поток: приняли → ужали →
  положили лёгкое; тяжёлый оригинал на диск не садится). Presigned-загрузка отклонена — противоречит
  «не хранить оригинал» и сложнее.
- Отложено (не в этой фиче): imgproxy/динамический трансформ, AVIF, миграция старых картинок.

## 3. Архитектура и компоненты

- **`ImageProcessor`** (новый) — чистая обработка: decode → strip metadata → resize (Lanczos, без
  апскейла) → encode WebP q82. На вход байты+тип, на выход набор `{variant → bytes}`.
  Библиотека: **Scrimage** (`scrimage-core` + `scrimage-webp`, бандлит `cwebp`); альтернатива —
  шелл к `libvips`/`cwebp` (финализируем в плане реализации по весу/скорости/образу Docker).
- **`MediaStorageService`** (новый) — работа с MinIO: put вариантов, get по id+variant, delete,
  init bucket. Инкапсулирует `MinioClient`.
- **`MediaController`** — тонкий: upload/get/delete, делегирует в сервисы. Валидация остаётся в
  `ImageUploadPolicy`.
- **MinIO** — хранит только сжатые варианты. **Cloudflare CDN** — кэш отдачи (immutable).
- **nginx** (`docker/frontend/nginx.conf`) — `client_max_body_size 20m`; проверить edge-прокси EasyPanel.

## 4. Поток загрузки (синхронный)

`POST /api/v1/media/upload` (multipart, поле `file`):
1. **Валидация** (`ImageUploadPolicy`): магические байты JPEG/PNG/WebP/GIF, размер ≤20MB,
   соответствие content-type; **гард на макс. входное разрешение** (напр. ≤8000px по стороне) —
   защита от декомпресионной бомбы.
2. **Decode + strip** метаданных.
3. **Генерация** `thumb/card/full` — все WebP q82, без апскейла (если оригинал меньше цели — берём как есть).
4. **Сохранение** в MinIO: `{id}_thumb.webp`, `{id}_card.webp`, `{id}_full.webp`
   (`id` = UUID; опц. хэш контента для дедупа — решить в плане).
5. **Ответ:** `{ id, url, variants: { thumb, card, full } }`, где `url` — дефолт (`full`),
   формат URL как раньше (`/api/v1/media/...`) для обратной совместимости.

## 5. Поток отдачи

- `GET /api/v1/media/{id}` → дефолтный размер; `GET /api/v1/media/{id}/{variant}` → конкретный.
- Заголовки: **`Content-Type: image/webp`**, **`Cache-Control: public, max-age=31536000, immutable`**.
- **Стриминг** из MinIO (не `readAllBytes`). Cloudflare кэширует на edge.
- Чинит текущие баги: `octet-stream` и отсутствие кэша.

## 6. Контракт и обратная совместимость

- Фронт хранит **один** URL (`logoUrl`/`coverUrl`/`coverImageUrl`/`iconUrl`/`avatarUrl`). Поле `url`
  (дефолт) кладётся как раньше → **существующий фронт не ломается**. Адаптивные `srcset` из `variants`
  фронт подключит позже, инкрементально (Фаза 2).
- **Старые сырые картинки** (`/api/v1/media/{oldfile}`) продолжают отдаваться как есть (объекты в MinIO
  остаются). Разовая миграция демо/логотипов в WebP — опционально, отдельным шагом.
- Публичный контракт upload расширяется (добавляется `id`/`variants`), но существующие поля
  (`url`) сохраняются — ломающих изменений нет.

## 7. Обработка ошибок

| Случай | Ответ |
|---|---|
| Пустой / не картинка / несоответствие типа | 400 |
| Больше 20MB (или nginx-лимита) | 413 |
| Не удалось декодировать/обработать | 422 «не удалось обработать изображение» |
| MinIO недоступен | 503 |
| Запрошенного файла/варианта нет | 404 |

## 8. Конфигурация (вынести в `application.yml`, чтобы крутить без пересборки)

- Размеры вариантов (`thumb/card/full` px), качество WebP, макс. входное разрешение.
- nginx `client_max_body_size 20m` (+ проверить edge-прокси EasyPanel).
- multipart `20MB` (как есть).

## 9. Тестирование

- **Unit `ImageProcessor`:** ресайз до целевых px без апскейла; выход — валидный WebP; EXIF снят;
  вес/качество в ожидаемом диапазоне; маленький оригинал не апскейлится.
- **Unit `ImageUploadPolicy`:** есть (магические байты) — дополнить негативами (bad-format, mismatch, oversize, empty).
- **`MediaController`:** happy-path (созданы 3 варианта, ответ содержит `variants`); oversize→413;
  bad-format→400; processing-fail→422; missing→404. Через мок `MinioClient` (как в текущем
  `MediaControllerTest` — пакетный конструктор).
- **Интеграция MinIO:** put/get вариантов — опционально через Testcontainers (в проекте сейчас не
  подключён; добавлять по решению в плане).
