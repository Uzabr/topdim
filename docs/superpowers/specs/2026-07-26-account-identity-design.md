# Спецификация: Идентичность и аккаунт (подсистема #1)

**Дата:** 2026-07-26 · **Статус:** утверждён владельцем · **Сервис:** identity-service (+ gateway для маршрутов входа)

## Context
У topdim появилось несколько способов входа (email+пароль, Telegram — уже live, скоро Google и телефон-OTP), но нет единой модели: как эти входы сводятся в один аккаунт, что происходит при коллизиях идентификаторов, как работает восстановление и уровни доверия. Отсутствие модели уже дало проблемы: placeholder-email `tg_*@topdim.uz` протекает в UI как настоящий; `auth/guest` выдаёт токен по телефону без OTP (Sybil-дыра); `trust_level` хранится, но не имеет чёткого определения. Эта спека фиксирует **поведение аккаунта во всех случаях** — фундамент, на который опираются верификация (#2), уведомления (#3) и trust/перки (#4).

Цель: один человек — один аккаунт без дублей; безопасное объединение способов входа по доказанному владению; встроенное восстановление; экономически бессмысленная многоаккаунтность.

## Модель аккаунта
- Аккаунт = внутренний `userId`.
- **Идентификаторы** (каждый уникален глобально, ≤1 на аккаунт): `email`, `phone`, `google_sub`, `telegram_chat_id`.
- **Роль** (GUEST/USER/PARTNER/MODERATOR/ADMIN/SUPER_ADMIN) и **уровень доверия** (L0/L1) — ортогональны.
- Флаги владения: `email_verified`, `phone_verified` (существуют). Идентификатор считается «доказанным», когда получен через владение: пароль+подтверждение (email), OTP (phone), oauth (google), deeplink+код (telegram).

## Поведение по методам

| Метод | Первый раз (идентификатора нет в базе) | Повторный вход | Привязка из авторизованной сессии |
|---|---|---|---|
| **Email+пароль** | создать аккаунт, `email_verified=false`, пароль задан, L0 | email+пароль | задать/сменить email → письмо на новый адрес → подтверждение |
| **Телефон (OTP)** | создать аккаунт, `phone_verified=true`, L0 | номер → OTP | номер → OTP |
| **Google** | создать аккаунт, email от Google `email_verified=true`, L0 | по `google_sub` | Google-oauth |
| **Telegram** | создать аккаунт, **placeholder** `tg_<id>@topdim.uz`, без пароля, L0 | по `telegram_chat_id` | «Подключить Telegram» (deeplink+код) |

`auth/guest` (телефон без OTP) — **упраздняется**, заменяется телефон-OTP входом (закрывает Sybil-дыру).

## Алгоритм разрешения входа (ключевое поведение)
**Вход методом M с идентификатором `id` (пользователь НЕ залогинен):**
1. Найти аккаунт по `id` в его колонке (`google_sub` / `telegram_chat_id` / `phone` / `email`). Найден → **войти** (это же покрывает восстановление).
2. Не найден, но метод доказал владение email/phone, совпавшим с существующим аккаунтом по другой колонке:
   - **Google**: email от Google совпал с аккаунтом, где `email_verified=true` → войти в него + привязать `google_sub`. Если у совпавшего аккаунта email **неподтверждён** → в тот аккаунт НЕ входим (email там лишь заявлен, не доказан): создаём/используем отдельный Google-аккаунт, email переносится на него (`email_verified=true`), а у старого аккаунта email освобождается (становится без email). Так реальный владелец почты не попадает в чужой «сквоттер»-аккаунт и не отдаёт свои данные.
   - **Телефон/Email**: совпадение по `phone`/`email` = это и есть тот аккаунт (уникальны) → вход.
3. Иначе → создать новый аккаунт (L0).

**Привязка методом M с `id` к текущему аккаунту B (пользователь ЗАЛОГИНЕН):**
- Если `id` уже принадлежит другому аккаунту A → **отказ «уже занято»** (без предложения перейти, без слияния).
- Иначе → привязать + пометить verified.

## Уникальность идентификаторов
Верифицированные `phone` и `email` **заперты за одним аккаунтом**: «один номер = один аккаунт», «одна почта = один аккаунт». Попытка верифицировать/привязать занятый идентификатор к другому аккаунту → отказ.

## Вход = восстановление
Доказательство владения идентификатором = вход в аккаунт-владелец. Поэтому:
- Потерял доступ (напр., только-Telegram + верифиц. телефон, Telegram утерян) → ввёл номер → OTP → **вошёл в свой аккаунт** (self-service восстановление). То же для email (письмо) и Google (oauth).
- Предложение восстановить показывается **только вне залогиненной сессии** (при попытке входа), не при добавлении идентификатора в сессии.

## Уровни доверия L0 / L1 (вычисляемый)
- `L1 = phone_verified ИЛИ (была успешная оплата)`.
- «Была оплата» — **исторический факт, навсегда** (флаг `has_paid`/`paid_at`, ставится по сигналу от payment-service). `phone_verified` — текущее состояние (сбрасывается при смене телефона).
- **Email-подтверждение НЕ поднимает до L1** (бесплатные почты — слабый анти-Sybil; email нужен для сброса пароля/уведомлений).
- L1 открывает перки (детали гейтинга — подсистема #4).

## Многоаккаунтность и анти-абьюз
- Несколько аккаунтов на разные идентификаторы **не запрещаем** (жёсткий запрет требует KYC).
- **Не даём** несколько аккаунтов на один верифицированный номер/почту (уникальность выше).
- **Перки дедуплицируются по верифицированному идентификатору** (телефон/карта), а не по аккаунту → много аккаунтов не даёт выгоды. Единица дедупликации (телефон / карта / оба) — детализируется в #4.

## Локаут
Настоящий локаут только при потере **всех** верифицированных идентификаторов (аккаунт без телефона/почты/Google, привязан лишь утраченный Telegram) → восстановление через поддержку. Профилактика: **при верификации телефона предлагать задать резервный метод** (email/пароль), чтобы не оставаться с единственным ключом.

## Влияние на модель данных (identity-service)
- Добавить `google_sub VARCHAR UNIQUE` (nullable) на `users` (миграция — номер занять по реестру, на 2026-07-26 следующий identity = V14).
- `has_paid`/`paid_at` на `users` — ставится сигналом от payment-service (payment→identity; identity сейчас без rabbit → через internal-эндпоинт или добавить listener; способ — в плане реализации).
- `trust_level` (существующая колонка от Telegram-работы) → **не источник правды**; L1 вычисляется из `phone_verified` + `has_paid`. Колонку либо убрать, либо пересчитывать; решить в плане.
- `phone` заполняется ТОЛЬКО через OTP (verified). Legacy-`phone` без подтверждения (register/guest) — грандфазер/очистка в плане.

## Вне объёма этой спеки (отдельные подсистемы/спеки)
- Реализация каналов: Eskiz SMS-клиент, SMTP (подсистема #3).
- Детали флоу верификации email/phone (подсистема #2).
- Гейтинг и дедупликация перков (подсистема #4).
- Матрица уведомлений «событие→канал» (#3).
- Фикс загрузки аватара — отдельная фронт-задача.

## Verification (как проверить поведение end-to-end)
- **Один аккаунт:** войти через Telegram (создаётся L0, placeholder email) → в профиле задать телефон+OTP → тем же телефоном войти в др. браузере без логина → попадаешь в ТОТ ЖЕ аккаунт (те же купоны).
- **Коллизия в сессии:** залогинен в аккаунте B → добавить телефон, привязанный к A → «уже занято», B не меняется, A нетронут.
- **Google-объединение:** есть email-аккаунт с verified email → войти через Google с тем же email → попадаешь в тот аккаунт, `google_sub` привязан (не дубль).
- **L1:** L0-аккаунт → verify телефон → `L1` истинно; сменить телефон на неподтверждённый без оплат → назад `L0`; совершить оплату → `L1` навсегда.
- **Анти-абьюз:** два аккаунта, один верифиц. телефон каждому нельзя одинаковый; перк «первый заказ» — один раз на телефон (проверяется в #4).
- **Sybil-дыра закрыта:** `auth/guest` без OTP больше не выдаёт токен.
