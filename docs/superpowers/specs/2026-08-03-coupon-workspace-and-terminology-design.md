# Спецификация: единое рабочее место купонов и терминология

**Дата:** 2026-08-03

**Статус:** утверждено владельцем продукта

**Контур:** `frontend/admin-app`, `frontend/partner`, `frontend/web-app`, `coupon-service`

## Контекст

Текущая админка распределяет один жизненный цикл купона между экранами «Все
купоны», «Канбан-доска», «Заявки партнёров», «Решения мерчанта» и «Создать
купон». Несколько экранов читают один `/api/v1/admin/coupons`, но используют
разные локальные лимиты и по-разному отображают одинаковые статусы. Сотруднику
приходится самостоятельно понимать, где находится нужный купон и какое действие
допустимо.

Одновременно интерфейсы используют слова «купон», «предложение», «акция»,
«оффер», «товар» и «продукт» для одной модели. В реализации нет отдельной
сущности акции или продукта: продаваемая сущность — `CouponOffer`, её варианты —
`CouponOption`, а результат покупки — `PurchasedCoupon`. Поэтому слово «акция»
не должно обозначать отдельный объект или основной раздел продукта.

## Цель

Создать единое рабочее место `/coupons`, в котором сотрудник видит полный
жизненный цикл купона, переключается между таблицей и Kanban, использует
серверные фильтры и выполняет только допустимые для его роли и статуса действия.
Одновременно привести пользовательские тексты к одной продуктовой терминологии
без переименования таблиц БД, Java-классов и существующих API-контрактов.

## Продуктовая терминология

### Основные понятия

| Контекст | Основной термин | Допустимое уточнение |
|---|---|---|
| Покупательский web | Купон | Купонное предложение |
| Partner app | Предложение | Купонное предложение |
| Admin app | Купон | Карточка купона |
| Внутренняя реализация | `CouponOffer` | Техническое имя не меняется |
| Результат покупки | Купленный купон | Сертификат допустим только как пояснение |

### Правила текстов

- «Акция» удаляется из навигации, заголовков форм, названий очередей и основных
  системных сообщений.
- В buyer flow используется «купон»: «Купить купон», «Мои купоны», «Похожие
  купоны».
- В partner flow используется «предложение»: «Мои предложения», «Подать
  предложение», «Название предложения», «Описание предложения».
- В admin flow используется «купон»: «Купоны», «Создать купон», «Купон ожидает
  партнёра».
- «Оффер» не используется в пользовательских текстах. В технических
  комментариях и именах полей `offerDescription` сохраняется.
- «Товар» заменяется на «купон» или «позиция» там, где интерфейс фактически
  работает с купонами, а не с отдельным товарным каталогом.
- Публичный бренд — `sizbiz`. Технические идентификаторы `topdim`, `uz.topdim`,
  `TOPDIM-QR:` и имена инфраструктуры не переименовываются этим проектом.

## Информационная архитектура

### Канонические маршруты

| Маршрут | Назначение |
|---|---|
| `/coupons` | Единое рабочее место |
| `/coupons/new` | Создание купона |
| `/coupons/:id/edit` | Редактирование допустимого купона |

Состояние рабочего места хранится в query string:

```text
/coupons?tab=in-progress&view=table&search=pizza&merchantId=12&page=2
```

Поддерживаемые параметры:

- `tab`: продуктовая группа статусов;
- `view`: `table` или `kanban`;
- `search`: поиск по названию купона и партнёру;
- `merchantId`: фильтр партнёра;
- `assignedModeratorId`: фильтр ответственного сотрудника;
- `page`: номер серверной страницы таблицы.

Поиск отправляется через 300 ms после последнего изменения строки. Таблица
использует `size=20`; пользователь может выбрать 20, 50 или 100 записей.
Kanban использует `size=20` отдельно для каждой колонки.

Неизвестные или недопустимые значения заменяются безопасными значениями:
`tab=new`, `view=table`, `page=0`. Поиск и выбранные фильтры сохраняются при
переключении вида, если они применимы к новому представлению.

### Совместимость старых ссылок

Старые маршруты не удаляются без переходного периода, а перенаправляются:

| Старый маршрут | Новый адрес |
|---|---|
| `/moderation/coupons` | `/coupons` |
| `/moderation/coupons/kanban` | `/coupons?view=kanban` |
| `/moderation/requests` | `/coupons?tab=new` |
| `/moderation/coupons/create` | `/coupons/new` |
| `/moderation/coupons/edit/:id` | `/coupons/:id/edit` |
| `/moderation/coupons/review` | `/coupons?tab=waiting-partner` |

### Вкладки

| Вкладка | URL key | Backend-статусы |
|---|---|---|
| Новые | `new` | `LEAD` |
| В работе | `in-progress` | `DRAFT` |
| Требуют изменений | `revision` | `REVISION_REQUESTED` |
| Ожидают партнёра | `waiting-partner` | `WAITING_FOR_MERCHANT` |
| Опубликованные | `published` | `ACTIVE`, `PAUSED`, `SOLD_OUT` |
| Архив | `archived` | `ARCHIVED` |

Вкладки показывают понятное название, а технический статус остаётся доступен в
карточке и таблице как дополнительный tag.

## Компоненты frontend

### `CouponWorkspacePage`

Корневой контейнер читает URL, нормализует состояние, выбирает таблицу или
Kanban и связывает toolbar, вкладки, данные и мутации. Контейнер не дублирует
правила ролей или статусов.

### `CouponWorkspaceToolbar`

Содержит:

- поиск с debounce;
- фильтр партнёра;
- фильтр ответственного сотрудника, когда он доступен роли;
- переключатель «Таблица / Kanban»;
- кнопку «Создать купон».

### `CouponStatusTabs`

Отображает шесть продуктовых групп статусов. Смена вкладки сбрасывает `page` в
`0`, но сохраняет поиск, партнёра и представление.

### `CouponTableView`

Использует серверную пагинацию. Таблица не выполняет локальную пагинацию
неполной выборки. Строка показывает купон, партнёра, понятный статус,
ответственного, ключевые сроки и доступные действия.

### `CouponKanbanView`

Показывает рабочие статусы отдельными колонками. Каждая колонка запрашивает свою
страницу и использует `totalElements`. Если записей больше загруженной страницы,
показывается «Показать ещё». Фиксированный запрос первых 500 записей удаляется.

### `CouponActionMenu`

Получает купон и роль, затем отображает результат чистой функции разрешений.
Компонент не содержит самостоятельных статусных правил.

### `couponWorkspaceState`

Отвечает только за:

- разбор query string;
- нормализацию значений;
- преобразование продуктовой вкладки в backend-статусы;
- построение следующего URL.

### `couponPermissions`

Возвращает допустимые действия для пары «роль + статус + ownership». Это единый
источник правил для таблицы, Kanban и формы.

## Правила действий

| Статус | MODERATOR | ADMIN / SUPER_ADMIN |
|---|---|---|
| `LEAD` | Взять в работу | Взять в работу |
| `DRAFT` | Редактировать свой, отправить партнёру | Редактировать, отправить партнёру |
| `REVISION_REQUESTED` | Редактировать свой, повторно отправить | Редактировать, повторно отправить |
| `WAITING_FOR_MERCHANT` | Просмотр, ожидание решения | Просмотр; служебное решение через отдельное подтверждение |
| `ACTIVE` | Просмотр | Просмотр, допустимое снятие с публикации |
| `PAUSED` | Просмотр | Просмотр, допустимое восстановление или архивирование |
| `SOLD_OUT` | Просмотр | Просмотр, архивирование по действующим правилам |
| `ARCHIVED` | Просмотр | Просмотр истории |

Backend остаётся источником истины. Скрытие кнопки во frontend не считается
авторизацией.

### Служебное решение за партнёра

- Не отображается отдельным пунктом меню.
- Доступно только `ADMIN` и `SUPER_ADMIN`.
- Перед отправкой показывается предупреждение, что штатный путь — решение
  партнёра в partner app или Telegram.
- Обязательна непустая бизнес-причина.
- Backend-метод получает серверную проверку роли; существующие partner и bot
  endpoints не меняются.
- Полный межсервисный audit trail остаётся самостоятельным проектом, но этот
  срез не должен оставлять служебную операцию без actor ID и причины в
  прикладном журналировании.

## Backend API

Существующий endpoint расширяется совместимо:

```http
GET /api/v1/admin/coupons
    ?status=LEAD
    &statuses=ACTIVE,PAUSED,SOLD_OUT
    &search=pizza
    &merchantId=12
    &assignedModeratorId=7
    &page=0
    &size=20
```

Правила совместимости:

- старый одиночный `status` продолжает работать;
- `statuses` используется для продуктовых групп с несколькими статусами;
- одновременная передача `status` и `statuses` возвращает `400 Bad Request`,
  чтобы исключить неоднозначность;
- `search` ищет без учёта регистра по названию купона и имени партнёра;
- `merchantId` фильтрует по точному ID партнёра;
- `assignedModeratorId` фильтрует по ответственному сотруднику;
- пагинация остаётся нумерованной с `page=0`;
- `size` по умолчанию равен `20`, допустимый диапазон — от `1` до `100`;
  значение вне диапазона возвращает `400 Bad Request`.

Для Kanban frontend делает отдельный paginated-запрос на колонку. Новый
неограниченный aggregate endpoint не создаётся.

## Поток данных

```text
URL
→ couponWorkspaceState
→ React Query key
→ GET /api/v1/admin/coupons
→ Page<CouponOfferResponse>
→ CouponTableView или CouponKanbanView
→ CouponActionMenu
→ mutation
→ targeted query invalidation
```

Мутация считается успешной только после успешного ответа backend. После `409`
текущая выборка обновляется, чтобы показать фактического ответственного или
новый статус.

## Ошибки и состояния

- Ошибка API никогда не отображается как пустая очередь.
- Ошибка загрузки показывает понятное сообщение, повтор и время последней
  успешной загрузки, если данные уже были получены.
- `401` использует общий session refresh flow.
- `403` объясняет отсутствие прав и не повторяет запрещённую мутацию.
- `404` сообщает, что купон был удалён или ссылка устарела.
- `409` сообщает, что запись уже изменена другим сотрудником, и обновляет данные.
- Network timeout сохраняет последние валидные данные, явно помечая их как
  устаревшие.
- Empty state зависит от вкладки: например, «Новых купонов нет» и «Нет купонов,
  ожидающих партнёра».
- Ошибка загрузки одной Kanban-колонки не скрывает успешно загруженные колонки.

## Тестовая стратегия

Работа выполняется через TDD. Первым implementation-этапом подключаются Vitest,
React Testing Library и общий test setup для `admin-app`.

### Frontend unit tests

- разбор и нормализация URL;
- преобразование вкладок в backend-статусы;
- сохранение применимых фильтров при переключении представления;
- матрица role/status/ownership;
- единый словарь терминологии без «акции» в целевых интерфейсах.

### Frontend component/integration tests

- старые маршруты перенаправляются на канонические;
- таблица передаёт серверные `page`, `size` и фильтры;
- Kanban загружает следующую страницу отдельной колонки;
- ошибка API не превращается в empty state;
- `409` показывает конфликт и запускает обновление;
- MODERATOR не видит служебное решение;
- ADMIN/SUPER_ADMIN видит служебное решение и не может отправить пустую причину;
- действия таблицы и Kanban используют одинаковую permission matrix.

### Backend tests

- одиночный `status` сохраняет прежнее поведение;
- `statuses` возвращает объединённую страницу;
- `status + statuses` отклоняется с `400`;
- поиск работает по купону и партнёру без учёта регистра;
- фильтры партнёра и ответственного комбинируются;
- страницы за пределами первых 50/100/500 записей доступны;
- MODERATOR получает `403` на служебное решение;
- ADMIN/SUPER_ADMIN проходит проверку роли;
- partner и bot approval flows не получают регрессию.

### Обязательная верификация этапа

- focused frontend tests текущего этапа;
- focused backend tests, если менялся backend;
- полный `npm run lint` для `frontend/admin-app`;
- полный `npm run build` для `frontend/admin-app`;
- затронутые Gradle test suites;
- `git diff --check`;
- просмотр списка изменённых файлов перед commit.

## Этапы реализации и delivery

1. Design spec.
2. Детальный implementation plan.
3. Тестовая инфраструктура `admin-app`.
4. Backend-фильтры и серверная пагинация.
5. Каркас `/coupons`, меню и redirects.
6. Табличное представление.
7. Пагинированный Kanban.
8. Централизованные действия и role rules.
9. Служебное решение за партнёра.
10. Терминология в `admin-app`, `partner` и `web-app`.
11. Полная regression-верификация и активная документация.

Каждый этап выполняется отдельно:

```text
failing test
→ подтверждённый RED
→ минимальная реализация
→ GREEN
→ lint/build/focused tests
→ git diff review
→ отдельный commit
→ push текущей ветки
```

Если проверка неуспешна, этап не коммитится и не отправляется. Каждый commit
должен содержать только файлы своего этапа и иметь понятное сообщение на уровне
продуктового результата.

## Вне объёма проекта

- Переименование `CouponOffer`, `CouponOption`, таблиц БД и существующих JSON
  полей.
- Полный редизайн партнёрского onboarding.
- Единый support center для жалоб, отзывов, вопросов и возвратов.
- Реальная платёжная интеграция и финансовая сверка.
- Полный межсервисный audit trail.
- Dashboard и продуктовая аналитика.
- Управление категориями и ситуациями.
- Bazaar/shop admin UI и выбор canonical directory service.
- Промокоды.

Эти контуры получают отдельные спецификации и implementation plans, чтобы
первый проект оставался независимо проверяемым вертикальным срезом.

## Критерии готовности

- Один пункт меню «Купоны» открывает единое рабочее место.
- Все старые coupon routes безопасно перенаправляются.
- Таблица и Kanban используют один URL state и одну permission matrix.
- Ни одна запись не становится недоступной из-за лимитов 50/100/500.
- Сотрудник отличает ошибку загрузки от пустой очереди.
- MODERATOR не может принять служебное решение за партнёра.
- Основные тексты admin/partner/web следуют утверждённой терминологии.
- Frontend и backend сценарии защищены автоматическими тестами.
- Каждый этап имеет отдельный проверенный commit и push.
