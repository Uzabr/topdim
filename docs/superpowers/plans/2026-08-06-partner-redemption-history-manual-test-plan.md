# Ручной тест-план истории погашений партнёра

**Цель:** проверить на реалистичных данных, что OWNER и MANAGER видят историю своего мерчанта, CASHIER — только собственные погашения, а поиск, даты, пагинация и обновление после PIN/QR работают без утечки данных.

**Среда:** только DEV/тестовый стенд. Продовые погашения и пользовательские данные не изменять.

**Фича:** `/redemptions` в partner cabinet и `GET /api/v1/partner/redemptions`.

## 1. Подготовка данных

Подготовить два независимых мерчанта.

| Контекст | Пользователи | Данные |
|---|---|---|
| Мерчант A | OWNER-A, MANAGER-A, CASHIER-A1, CASHIER-A2 | Не менее 45 погашений за разные даты |
| Мерчант B | OWNER-B, CASHIER-B1 | Не менее 5 погашений с похожими кодами |

Для мерчанта A нужны записи:

- CASHIER-A1 и CASHIER-A2 должны иметь собственные погашения;
- коды `CP-VIP-001`, `CP-VIP-002`, `CP-STANDARD-001`;
- код с буквами разного регистра;
- код, содержащий буквальные `%`, `_` и `!`;
- погашение ровно в `00:00:00` первого дня периода;
- погашение в `23:59:59` последнего дня периода;
- записи непосредственно до и после выбранного периода;
- две записи с одинаковым `redeemedAt`, созданные последовательно;
- минимум один активный купон для PIN-погашения;
- минимум один активный купон с QR для QR-погашения;
- использованный, истёкший и принадлежащий мерчанту B купоны для negative cases.

Зафиксировать ожидаемое количество записей для каждого мерчанта и кассира до начала проверки.

## 2. Доступ и изоляция

### M-01 — OWNER видит историю мерчанта

1. Войти как OWNER-A.
2. Открыть пункт «История погашений».
3. Проверить прямой переход на `/redemptions`.

Ожидается: видны записи CASHIER-A1, CASHIER-A2 и владельца; записей мерчанта B нет.

### M-02 — MANAGER видит историю мерчанта

Повторить M-01 как MANAGER-A.

Ожидается: merchant-wide история мерчанта A; управление сотрудниками недоступно согласно существующим правам.

### M-03 — CASHIER видит только себя

1. Войти как CASHIER-A1.
2. Открыть историю через меню и прямой URL.
3. Найти известные коды CASHIER-A1 и CASHIER-A2.

Ожидается: видны только погашения CASHIER-A1; записи CASHIER-A2, владельца и мерчанта B отсутствуют.

### M-04 — подмена scope не работает

Открыть:

```text
/redemptions?merchantId=<merchant-B>&staffId=<cashier-A2>
```

Ожидается: неизвестные параметры удаляются при нормализации URL или игнорируются; trusted scope пользователя не меняется. В сетевом запросе UI нет `merchantId` и `staffId`.

### M-05 — повреждённый контекст закрывается безопасно

На тестовой сессии проверить CASHIER-контекст без `staffId` и неизвестную роль.

Ожидается: история не выдаётся; backend возвращает контролируемую ошибку, без merchant-wide fallback и без `500`.

## 3. Поиск и даты

### M-06 — частичный регистронезависимый поиск

Искать `vip`, `CP-VIP`, код в нижнем регистре и код с пробелами по краям.

Ожидается: совпадения ищутся по части кода без учёта регистра; пробелы по краям не влияют.

### M-07 — буквальные wildcard-символы

Искать `%`, `_`, `!` и полную комбинацию тестового кода.

Ожидается: символы трактуются буквально и не расширяют выборку как SQL wildcard.

### M-08 — отдельные границы периода

Проверить только «Дата от», только «Дата до» и обе даты вместе.

Ожидается: каждая граница работает независимо; выбранная дата окончания включается полностью.

### M-09 — точные календарные границы

Выбрать период с подготовленными записями в `00:00:00` и `23:59:59`.

Ожидается: обе записи включены; запись до начала и запись с `00:00:00` следующего дня исключены.

### M-10 — повреждённые URL-фильтры

Открыть по очереди:

```text
/redemptions?from=2026-02-31&page=-2
/redemptions?from=2026-08-07&to=2026-08-06&page=2
/redemptions?page=not-a-number
```

Ожидается: URL заменяется нормализованным; запрос не приводит к `500`; перевёрнутый диапазон удаляется.

### M-11 — backend validation

Через DevTools или API-клиент отправить `page=-1`, `size=0`, `size=101`, нечисловые page/size, код длиннее 50 символов, невозможную дату и перевёрнутый период.

Ожидается: `400`, `success=false`; access scope не вычисляется для заведомо невалидного запроса.

## 4. Пагинация и порядок

### M-12 — первая и последующие страницы

1. Сбросить фильтры.
2. Проверить 20 строк на первой странице.
3. Перейти на страницы 2 и 3, затем вернуться назад браузером.

Ожидается: URL содержит one-based `page`; backend получает zero-based `page`; строки не дублируются и не пропадают; back/forward восстанавливает фильтры и страницу.

### M-13 — стабильный порядок

Ожидается: новые погашения выше старых; при одинаковом `redeemedAt` запись с большим ID идёт первой.

### M-14 — фильтр сбрасывает страницу

На странице 3 применить поиск или даты.

Ожидается: URL возвращается на первую страницу; backend получает `page=0`.

## 5. Состояния интерфейса

### M-15 — полностью пустая история

Открыть историю мерчанта без погашений.

Ожидается: «Погашений пока нет».

### M-16 — пустой результат фильтра

Искать отсутствующий код.

Ожидается: «По заданным фильтрам ничего не найдено»; «Сбросить» очищает URL и возвращает полную историю.

### M-17 — ошибка и повтор

Временно заблокировать запрос истории в DevTools или использовать согласованную тестовую недоступность order-service.

Ожидается: «Не удалось загрузить историю погашений»; после восстановления связи кнопка «Повторить» загружает тот же фильтр.

## 6. Обновление после погашения

### M-18 — успешный PIN

1. Открыть историю и запомнить верхнюю запись/счётчик.
2. Перейти в «Погашение», успешно погасить подготовленный PIN.
3. Вернуться в историю.

Ожидается: выполняется новый GET; свежее погашение находится на первой странице и соответствует пользователю/способу `PIN`.

### M-19 — успешный QR

Повторить M-18 через QR.

Ожидается: история обновляется, новая запись имеет способ `QR`.

### M-20 — неуспешное погашение

Проверить использованный, истёкший, неизвестный и принадлежащий мерчанту B купоны.

Ожидается: понятная ошибка; новой записи нет; существующая история не подменяется ложным успехом.

## 7. Визуальная и адаптивная проверка

Проверить desktop и узкий экран:

- меню и активное состояние «История погашений»;
- сворачивание sidebar;
- фильтры без недоступных кнопок;
- горизонтальный scroll таблицы;
- читаемость кода, сотрудника, способа и даты;
- отсутствие branch/export/staff/method фильтров и dashboard-ссылки, которые не входят в первый релиз.

## 8. Performance-снимок

На наборе не менее 10 000 погашений одного мерчанта зафиксировать:

- время первого запроса и перехода на далёкую страницу;
- `EXPLAIN ANALYZE` для запроса без фильтров и с cashier/date/code фильтрами;
- число прочитанных строк и наличие сортировки;
- решение, нужен ли composite index `(merchant_id, redeemed_at, id)` и вариант со `staff_id`.

До согласования продуктового SLA результат фиксируется как измерение, а не как автоматический pass/fail. Если наблюдается заметная деградация, индекс оформляется отдельной миграцией и задачей.

## 9. Фиксация результатов

Для каждого сценария записать:

| Поле | Значение |
|---|---|
| Статус | PASS / FAIL / BLOCKED |
| Роль и мерчант | Без персональных данных |
| Ожидалось | Кратко |
| Получено | Кратко |
| Evidence | Screenshot, request/response без токенов, timestamp |
| Дефект | Ссылка и severity |

## 10. Критерии завершения ручного этапа

- M-01—M-20 выполнены;
- нет cross-merchant и cross-cashier утечек;
- нет неожиданных `500`;
- количество и порядок записей совпадают с подготовленными данными;
- PIN и QR добавляют корректную запись, ошибки не добавляют;
- network-запрос UI не содержит клиентских `merchantId/staffId`;
- performance-снимок рассмотрен и решение по индексу зафиксировано;
- все P0/P1-дефекты исправлены и перепроверены.
