# Admin launch manual test plan

> Статус: подготовлен, но ещё не выполнен. План запускается только на локальном
> demo-окружении или отдельном QA-стенде. Production-данные не использовать.

## 1. Цель и продуктовая граница

Проверить, что `admin-app` готов к запуску как операционная панель купонного MVP:

- `MODERATOR` обрабатывает купоны, отзывы и жалобы;
- `ADMIN` дополнительно управляет возвратами, мерчантами, категориями, заказами,
  пользователями и партнёрскими заявками;
- `SUPER_ADMIN` дополнительно управляет сотрудниками и видит identity audit log.

В этот запуск не входят отдельные roadmap-модули базаров/магазинов, UI промокодов,
системные настройки и финансовая отчётность `SUPER_ADMIN`. Реальные платёжные
провайдеры, email/SMS delivery и единый межсервисный audit также проверяются
отдельно после появления production-контрактов.

## 2. Подготовка окружения

1. Запустить backend и инфраструктуру:

   ```bash
   ./scripts/dev/start-demo.sh
   ```

2. Создать/обновить локальные demo-данные:

   ```bash
   ./scripts/dev/seed-demo.sh
   ```

3. Запустить три SPA в отдельных терминалах:

   ```bash
   cd frontend/web-app && npm run dev
   cd frontend/admin-app && VITE_API_URL=http://localhost:8080 npm run dev
   cd frontend/partner && VITE_API_URL=http://localhost:8080 npm run dev
   ```

4. Проверить URL:

   - web-app: `http://localhost:5173`;
   - admin-app: `http://localhost:3001`;
   - partner-app: `http://localhost:3002`;
   - gateway: `http://localhost:8080`.

## 3. Матрица тестовых данных

Основной seed создаёт пользователей, мерчантов, филиалы и купоны. Во время прогона
нужно дополнительно получить через реальные UI/API-флоу:

- партнёрскую заявку `PENDING` и одну заявку, которую можно довести до `PROCESSING`;
- купоны в `LEAD`, `DRAFT`, `WAITING_FOR_MERCHANT`, `REVISION_REQUESTED`, `ACTIVE`,
  `PAUSED` и `ARCHIVED`;
- оплаченный заказ и купленный купон с известным PIN;
- возвраты `PENDING` и `APPROVED_PROCESSING`;
- жалобу `OPEN` и отзыв `PENDING`;
- неиспользуемую категорию и категорию, связанную с купоном;
- обычного пользователя для block/unblock;
- временного `MODERATOR` для проверки staff-операций.

Не менять состояния прямым SQL, если их можно получить штатным endpoint. SQL
допустим только для подготовки отсутствующего внешнего события; такой шаг нужно
зафиксировать в отчёте.

## 4. P0 — доступ и навигация

### 4.1 MODERATOR

- В меню есть Dashboard, Купоны, Жалобы и Отзывы.
- Нет Возвратов, Справочников, Заказов, Пользователей и Системы.
- Прямые URL `/support/refunds`, `/catalog/categories`, `/orders/list`,
  `/users/list`, `/system/staff` ведут на 403 и не загружают закрытые данные.

### 4.2 ADMIN

- Доступны все операционные разделы, кроме `/system/staff` и `/system/audit`.
- Прямой переход в системные разделы даёт 403.

### 4.3 SUPER_ADMIN

- Доступны все разделы текущего admin MVP.
- Logout очищает сессию; повторный direct URL ведёт на login.

Критический дефект: закрытый экран или данные доступны неподходящей роли.

## 5. P0 — dashboard

- ADMIN/SUPER_ADMIN видит сегодняшние заказы, оплаченную выручку, активные купоны,
  пользователей, жалобы, график за 7 дней и последние заказы.
- MODERATOR не вызывает и не показывает выручку, заказы и пользователей; видит
  очереди купонов и жалоб.
- Сверить числа с созданными в этом прогоне заказами и статусами, включая нулевые
  дни графика.
- При остановленном order-service данные заказов отображаются как недоступные, а
  не как ложный ноль; повтор после запуска сервиса восстанавливает блок.

## 6. P0 — рабочее место купонов

- Table и Kanban показывают одинаковые купоны; фильтры, поиск, пагинация и
  `Загрузить ещё` не дублируют записи.
- Старые URL `/moderation/...` сохраняют фильтр и ведут в единое рабочее место.
- Проверить переходы `LEAD → DRAFT → WAITING_FOR_MERCHANT`.
- Решение партнёра в partner-app: approve делает купон `ACTIVE`, revision —
  `REVISION_REQUESTED` с причиной.
- MODERATOR не видит служебное решение за партнёра. ADMIN/SUPER_ADMIN может
  выполнить его только с непустой бизнес-причиной.
- Повтор действия, конфликт двух вкладок, 403 и 404 показывают понятный ответ и
  не оставляют карточку в ложном состоянии.
- ACTIVE купон нельзя произвольно редактировать; pause/resume/archive доступны
  только разрешённым ролям и статусам.

## 7. P0 — партнёрская заявка и мерчант

- Создать заявку через `/partners`, увидеть её в admin-app и проверить локальные
  статусы и фильтр.
- Одобрение создаёт ровно одного пользователя и одного мерчанта.
- Если удалённо создать мерчанта не удалось, заявка остаётся `PROCESSING`, а
  повтор использует того же пользователя и не требует новый пароль.
- Reject требует причину и не допускает повторного решения.
- В карточке мерчанта проверить edit, activate/deactivate и список купонов.
- При редактировании филиалов сохраняются их ID и координаты; удалённый из формы
  филиал деактивируется, а не удаляется физически. Чужой/повторный location ID
  отклоняется.

## 8. P0 — категории

- Список содержит активные и выключенные категории.
- Создать категорию со всеми полями, отредактировать, выключить и включить.
- Дубликаты name/slug отклоняются; slug нормализуется.
- Неиспользуемая категория удаляется после подтверждения.
- Связанная с купоном категория остаётся в списке и возвращает конфликт; её можно
  деактивировать.
- Импорт `.xlsx` показывает количество добавленных/пропущенных строк, а upload
  иконки возвращает реальный URL.

## 9. P0 — заказы и купленный купон

- Список показывает business order number, локальный статус и корректную сумму,
  включая `0`.
- Фильтры `COMPLETED` и `REFUND_REQUESTED` работают.
- Ответ list/detail не содержит `qrToken`, relation graph или другие redemption
  secrets.
- Поиск купона: валидный код нормализуется, пустой запрос не отправляется, 404
  отличается от service/permission error, смена кода очищает старый результат.

## 10. P0 — пользователи и staff

- Поиск пользователя по телефону вместе с ролью применяет оба фильтра.
- Обычный USER/PARTNER блокируется только после подтверждения; повторная команда
  идемпотентна; ADMIN/SUPER_ADMIN защищён.
- SUPER_ADMIN создаёт только ADMIN или MODERATOR. Слабый и распространённый
  пароль отклоняется точной ошибкой.
- Смена роли и block/unblock инвалидируют старую сессию сотрудника.
- Нельзя изменить роль, заблокировать или удалить самого себя либо другого
  SUPER_ADMIN.
- Два одновременных запроса не создают двойное изменение security version.

## 11. P0 — support

### Возвраты

- `PENDING → APPROVED_PROCESSING → REFUNDED` и `PENDING → REJECTED`.
- Reject требует причину; complete подтверждает, что выплата уже сделана вручную.
- Повтор/две вкладки дают conflict, а не двойную обработку.

### Жалобы

- OPEN-жалоба решается или отклоняется с обязательным ответом.
- Повторное и конкурентное решение отклоняется.
- `IN_REVIEW` не тестировать как take-to-work: операции назначения пока нет.

### Отзывы

- Pending review показывает автора.
- Approve требует подтверждение; reject требует причину до 255 символов.
- После решения запись исчезает из pending; повтор даёт conflict.

## 12. P1 — audit, ошибки и UX

- Экран `Аудит сотрудников` показывает реальный `userId`, действие, объект, детали и время после
  create/change-role/block операций.
- Не ожидать email инициатора или IP: backend пока их не возвращает.
- Empty, loading, retry и pagination проверить на каждом списковом экране.
- При 401 выполняется refresh один раз; при неуспехе пользователь выходит.
- Проверить desktop 1440 px и узкое окно 768 px: таблицы остаются доступными,
  модальные окна не теряют кнопки подтверждения.

## 13. Критерии запуска

Запуск блокируется, если найдено хотя бы одно:

- P0 happy path не завершается;
- нарушение ролей или утечка redemption/security данных;
- двойная финансовая/статусная операция;
- ложный dashboard ноль при недоступном сервисе;
- потеря или физическое удаление связанного филиала;
- 500 вместо ожидаемых 400/403/404/409 в штатном негативном сценарии.

Допускаются только заведённые P2/P3 visual defects и известное предупреждение о
крупном frontend chunk. После прогона приложить аккаунт/роль, шаги, ожидаемый и
фактический результат, response body, screenshot и severity каждого дефекта.
